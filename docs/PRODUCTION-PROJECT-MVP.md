# 生产项目工具 MVP

> 状态：产品决策基线 · 2026-08-19
>
> 本文是当前“教科书式生产项目工具”的唯一产品决策入口。代码、UI 和其他设计文档都必须先对齐本文；本文没有决定的能力暂不实现。

## 1. 产品目标

my-agent 面向真实软件项目，帮助一个人或小团队按照成熟研发习惯完成从需求到发布的闭环：

```text
明确目标 → 形成设计 → 拆出任务 → 编码实现 → 测试验证 → 人工发布
```

它不是通用聊天助手，也不是文档填写器。聊天只是入口，项目文件、代码和测试结果才是工作结果。

## 2. 对齐大厂的原则

只吸收能直接提高交付质量的实践：

| 实践 | 本地项目等价物 |
|---|---|
| PRD / Project brief | `PROJECT.md` |
| Design doc / RFC | `DESIGN.md` |
| Issue / Sprint backlog | `TASKS.md` |
| CI / Test plan | `VERIFY.md` + 实际测试命令 |
| Code review | 任务级变更审阅和人工确认 |
| Release checklist | 发布前人工检查 |

暂不复制云端组织、多人审批、复杂权限、完整 Jira/PR 系统或固定七文件模板。

### 2.1 两层产品契约

本项目的生产流程分为 Harness 层和用户层。Harness 层负责约束 LLM：阶段权限、工具调用、任务授权、验证证据、审查和发布门必须真实执行；用户层只负责目标、范围、方案取舍、风险接受和最终发布确认。

内部规则不得反向变成用户的操作清单。默认界面不得要求用户理解 `phase`、`Gate`、`M1/M2`、任务归档、审查队列或工具白名单，也不得因为内部状态变化连续弹出“确认/关闭”动作。只有当内部判定改变用户下一步选择时，才转换为一条用户可理解的决策信息。

用户层的最小信息面固定为：

```text
当前目标 · 当前进展 · 需要我决定什么 · 结果/下一步
```

其余状态留在 Harness、过程详情或开发诊断中。任何内部状态进入默认界面，都必须说明它对应的用户决策；说不出对应决策的状态不得进入主路径。

## 3. 四个核心制品

项目默认只要求以下四个文件：

| 文件 | 唯一职责 | 必须回答的问题 |
|---|---|---|
| `PROJECT.md` | 项目章程 | 为什么做？给谁做？做什么和不做什么？ |
| `DESIGN.md` | 需求与设计 | 用户怎么用？方案怎么实现？关键决策是什么？ |
| `TASKS.md` | 当前执行队列 | 现在做什么？每项交付什么？依赖什么？ |
| `VERIFY.md` | 验证计划与证据 | 如何证明完成？实际结果是什么？ |

以下内容按需写入四个核心制品，不单独制造门槛：

- 范围、用户故事、验收标准：写入 `PROJECT.md` 或 `DESIGN.md`。
- 技术架构、API、数据模型、ADR：写入 `DESIGN.md`。
- 发布、迁移、回滚：写入 `VERIFY.md` 的发布检查章节，达到复杂度后再拆文件。
- 环境说明：保留 `ENV.md` 作为运行辅助信息，不参与核心完成判定。

## 4. 真源关系

每类事实只有一个真源，其他文件只引用稳定 ID，不复制正文：

```text
PROJECT.md
  └─ REQ-* / AC-*
       └─ DESIGN.md：UX-* / TD-* / ADR-*
            └─ TASKS.md：任务引用 REQ/AC/设计 ID
                 └─ VERIFY.md：验证引用 AC/任务 ID，记录真实证据
```

规则：

1. 范围和验收标准不能只存在于聊天记录。
2. 任务不能没有交付物和验收引用。
3. 验证结果必须来自实际命令、测试或明确的人工步骤。
4. 设计变更必须标明影响的需求、任务和验证项。
5. 同一事实发生冲突时，以更上游的制品为准，并把下游标记为待更新。

## 5. 最小启动标准

创建项目时不要求把文档写完整。满足下面四项即可开始第一轮工作：

- `PROJECT.md` 有目标、用户、范围和非目标。
- `DESIGN.md` 至少有一个用户流程、一个技术方案和一个验收标准。
- `TASKS.md` 至少有一个可执行任务。
- `VERIFY.md` 有对应的验证方法和预期结果。

不适用的章节写明“不适用及原因”，不使用空白模板假装完成。

## 5.1 需求输入与执行边界

用户提供项目简介、背景、目标、用户场景或功能列表时，默认这是**需求输入**，不是执行命令。

需求输入阶段必须：

- 先归纳已知目标、用户、范围和待确认问题；
- 说明当前处于需求阶段；
- 等待用户确认后，才进入文档整理或设计讨论；
- 不调用写文件、脚手架、工具创建、安装依赖、启动服务或其他有副作用的工具。

只有同时满足以下条件，Agent 才能执行写入或运行操作：

1. 用户明确提出了动作，例如“创建”“修改”“运行”“验证”或“开始实现”；
2. 动作对象和目标路径/项目明确；
3. 当前会话已绑定目标项目；
4. 所需的需求、设计和验证前置条件已经满足，或用户明确接受先生成文档草稿；
5. 工具确认通过。

实现契约：`active_shell=project` 但未同时绑定有效 `project_root` 时，写入、代码修改、命令执行、测试、服务启动、脚手架和工具创建等副作用调用必须在工具执行前拒绝；只读分析工具仍可用。拒绝结果必须说明“未绑定项目”，并指向打开或新建项目，不得通过换路径继续尝试。

以下内容不等于执行授权：

- 仅粘贴项目简介或需求文档；
- 说“这是我的项目”“帮我看看”但未指定动作；
- 附带截图、代码或文档但未要求修改；
- Agent 自己推断“下一步应该创建脚手架/工具”。

未绑定项目时，项目窗口只能进行只读分析和需求澄清。特别禁止：

- 创建或修改 `workspace/` 项目文件；
- 创建或修改 `evolve/tools/` 工具；
- 安装依赖、执行 shell、启动服务；
- 把需求描述自动转成脚手架或代码。

## 5.2 工具失败与停止规则

工具失败后，Agent 必须先解释失败原因和影响，再决定是否需要用户选择下一步：

- 参数或 schema 校验失败：最多自动修正一次；修正仍失败则停止；
- 权限、路径、项目绑定或确认失败：立即停止，不换路径盲试；
- 网络、依赖或服务失败：报告原始错误，改策略前等待用户确认；
- 同一回合累计两个不同工具失败：停止当前执行段，不继续扩大副作用。

失败熔断后不得继续输出“已完成”“工具可用”或“项目已生成”。

实现契约：参数修正以 `tool + normalized arguments + error code/message` 形成回合内指纹；同一指纹只允许一次免费修正。第二次仍失败时立即停止工具循环，保留结构化失败结果和原始原因，不再把失败调用标记为成功。命令退出码、权限拒绝、用户拒绝、超时和业务执行失败不进入免费参数修正。

## 6. 三个硬门槛

### 6.1 开始编码

一个任务允许进入编码，当且仅当：

- 任务有明确交付物；
- 任务引用 `PROJECT.md` 或 `DESIGN.md` 中的需求/验收 ID；
- 设计方案已经足够支撑本任务；
- `VERIFY.md` 已写出对应验证方法。

### 6.2 任务完成

一个任务允许标记完成，当且仅当：

- 代码或文档已经实际落盘；
- 对口测试、构建或人工验证已经执行；
- 验证结果成功，或失败原因与后续任务已记录；
- `TASKS.md` 记录了对应证据。

聊天中的“完成了”不构成完成证据。

### 6.3 版本发布

一个版本允许发布，当且仅当：

- 关键任务全部完成；
- 关键验收项在 `VERIFY.md` 中有成功证据；
- 发布、迁移和回滚检查已完成或明确豁免原因；
- 用户进行最后一次人工确认。

发布确认不自动触发，不以文档数量或任务数量代替测试结果。

### 6.3.1 任务队列与项目完成的区分

`TASKS.md` 的开放队列清空，只能证明当前任务批次没有待执行项。它不证明项目已经交付，也不允许 UI 或 Agent 直接显示“项目已完成”。清空后必须继续经过验证证据、交付审查、发布检查和用户人工确认；只有最后一项回执写入后，项目才进入完成态。

因此，所有任务列表、项目列表、顶栏和目标卡统一使用以下口径：

- 有开放任务：显示开放任务进度；
- 开放任务为零且尚未验证：显示“任务已清空 · 待验证”；
- 验证通过但尚未人工确认：显示“待发布验收”；
- 发布检查通过且人工验收已记录：才显示“项目已完成”。

## 6.4 项目主链路

项目工作按以下顺序推进。阶段是权限边界，不是额外的文档负担：

```text
需求输入 → 需求确认 → 文档整理 → 设计确认 → 小任务实现 → 验证 → 人工发布
```

| 阶段 | Agent 可以做什么 | Agent 禁止做什么 | 出口 |
|---|---|---|---|
| 需求输入 | 归纳背景、目标、用户、范围，提出问题 | 写文件、造工具、跑命令、启动服务 | 用户明确进入文档整理 |
| 需求确认 | 根据反馈修正理解，列出待确认事项 | 把沉默当同意，提前实现 | 用户确认目标和范围 |
| 文档整理 | 生成/更新四个核心制品草稿，拆出任务 | 直接修改业务代码或执行构建 | 四个制品具备最小启动内容 |
| 设计确认 | 解释方案、比较取舍、修订设计 | 未确认就进入实现 | 用户确认本批次设计 |
| 小任务实现 | 只实现当前任务，调用必要工具 | 扩大范围、顺手造工具、跳过前置条件 | 代码/文档已落盘 |
| 验证 | 执行对口测试，记录成功或失败证据 | 把工具调用成功等同于功能完成 | `VERIFY.md` 有真实结果 |
| 人工发布 | 整理发布检查和回滚信息 | 自动宣布发布或自动关闭里程碑 | 用户明确确认发布 |

### 6.4.1 权限状态

权限随阶段变化，不由 Agent 自行提升：

```text
requirements  →  documentation  →  design  →  implementation  →  verification  →  release
   只读              文档写入          设计写入        代码/测试工具          验证工具          人工确认
```

- `requirements`：默认状态；模型不接收工具 schema，内核拦截工具调用。
- `documentation`：只允许项目文档写入；不允许修改业务代码。
- `design`：允许更新设计和任务；不允许宣称实现完成。通过「项目 确认设计」进入此阶段。
- `implementation`：只开放当前任务需要的代码和测试工具；通过「项目 开始任务 T-001」授权一个具体任务后进入。
- `verification`：只运行与任务或验收项关联的验证；结果必须落证据。
- `release`：只生成发布检查并等待用户确认，不自动发布。

任何阶段都不能通过“我认为应该继续”自动提升权限。用户明确动作、项目绑定和前置出口同时满足后，内核才允许进入下一阶段。

### 6.4.2 设计确认与任务授权

文档整理完成后，必须经过两个独立动作：

1. `项目 确认设计`：检查四个核心制品中的 `REQ-*`、`AC-*`、`UX-*`、`TD-*`、`T-*`、`V-*` 引用，进入 `design`，不开放业务代码。
2. `项目 开始任务 T-001`：只接受 `TASKS.md` 中开放的任务 ID，记录当前任务并进入 `implementation`；完成该任务后回到验证，不自动启动下一任务。

旧项目仍兼容 `项目 确认`，但新建项目按上述两步推进。

### 6.4.3 文档整理期的提示策略

文档生成是一个连续批次，不把每次状态刷新都变成一次交互打断：

- `documentation` 阶段的文档完整性、基线缺项等 `warning` 只作为内部状态收集，不显示需要用户逐次关闭的“计划提示”。界面只保留轻量的“文档整理中”进度感知。
- 同一批次内的提示按文案去重；进入下一阶段时一次性汇总，并提供统一的计划/设计审阅入口。
- 用户关闭汇总提示后，在提示内容没有变化前不重复展示；出现新的缺项、真实错误或状态变化时重新提示。
- 写入失败、权限失败、阶段越权和其他会阻止继续执行的真实错误仍然立即打断，不能被批次汇总吞掉。

这条规则将“文档生成”和“计划审阅”解耦：连续生成四个核心制品时保持工作流连续，文档批次完成后再集中处理计划决策。

实现契约：`documentation` 是一个批次状态，而不是四次独立的计划事件。批次期间只保留轻量进度和累计数量；普通 warning、质量建议、计划搭档结果和可采纳卡暂存，不在侧栏弹出关闭式提示，也不打开计划审阅。权限失败、写入失败、阶段越权和真实执行错误不属于普通 warning，必须即时显示。

### 6.4.4 阶段卡的阻塞口径

阶段卡中的“本阶段阻塞”必须与执行内核使用同一份出口判定：

- 只有当前阶段出口缺失、`L2 stale`、权限失败或真实执行错误，才能进入 `execution_stage_blockers` / `execution_stage_missing`。
- 文档 `skeleton` / `draft`、内容 lint 的建议项（例如图示或引用完整度）属于待完善或审阅建议，不得直接标为当前阻塞。
- 对话总结、计划伙伴和侧栏展示必须引用同一状态；若没有阻塞，三处都应明确显示“没有发现阻塞文档”。

`content_lint` 仍可保留在状态中供计划建议使用，但不能绕过上述规则把建议项升级为阶段门禁。

### 6.4.5 运行提醒与计划提案分流

计划状态中的消息分为两类，不能混用：

- **运行提醒**：耗时较长、连续多轮未完成、建议检查任务粒度等观察性信息。它们只提供状态感知，不带可采纳动作，不进入 `suggestions`，也不打开计划审阅面。
- **计划提案**：会新增、删除、移动、拆分任务或修改项目文档的变更。它们必须带明确的 gated action，进入 `suggestions`，由用户在计划审阅中采纳或忽略。

运行提醒不能因为“可以顺便拆分”就伪装成计划提案。用户若确实要拆分，必须明确提出拆分动作，系统再生成可审阅的变更预览。

实现契约：计划审阅入口只能由 `suggestions` 中带有效 gated `action` 的卡片驱动；`operational_notices`、普通 `partner_notices` 和 `warnings` 不得单独打开计划审阅。前端不得根据“待审阅”“待采纳”等文案猜测存在提案；没有有效 action 时只能展示运行提醒或“当前没有可采纳提案卡”。阶段 warning 使用“待完善/不阻塞当前运行”语义，不暗示必须进入计划审阅。

### 6.4.6 狂奔运行授权

项目会话增加一个默认关闭的 `runaway` 运行授权。它允许 Harness 在同一项目内自动完成“拆解 → 实现 → 测试 → 修复 → 验证 → 下一任务”的连续循环，但不能让模型自行扩大权限或伪造完成。

狂奔开启后，内核必须维护可恢复的运行检查点：当前任务、任务完成基线、工具轮次、修复次数、最近验证结果和暂停原因。检查点落在会话元数据或项目运行状态中，前端状态丢失、窗口重启或网络重连不能导致重复执行或跳过验证。

当前实现将检查点持久化在 `SessionMeta`：当前任务、`project_runaway_checkpoint`、任务完成基线、工具轮次、`project_runaway_repair_count`、`project_runaway_last_verification`、错误指纹和 `project_runaway_paused_reason`。狂奔是后台可恢复运行，不以单次用户回合为边界；验证失败默认最多自动修复 3 次；同一错误指纹再次出现直接暂停，并通过 `project.state.runaway_status` 输出用户语言状态。

狂奔的用户契约：用户只需在项目内提交一次目标并显式开启狂奔，之后可以关闭窗口或离开，不需要逐项确认计划、任务、阶段或“继续”。系统回来时必须能从持久化检查点恢复；若尚未交付，只能显示自然语言进展或真实暂停原因，不能把内部状态伪装成“等待用户确认”。

狂奔授权覆盖矩阵：项目根目录内的代码/文档写入、测试、构建、普通依赖安装、本地服务启动与验证自动执行；宿主机写入、敏感文件、删除或清理、`git push`、外部网络写入、上下文切换和发布动作不在覆盖范围内。`plan_partner` 的计划提案属于项目内部控制面，狂奔下自动采纳，不再要求用户点击“确认提案”。

狂奔允许自动推进的范围：

- 已绑定项目内、已确认范围内的文档、代码、测试和验证；
- 当前任务完成后的下一条开放任务选择；
- 对验证失败的有限、同范围修复与重新验证；
- 普通阶段切换和内部任务授权。

狂奔必须暂停的范围：

- 需求或验收标准存在无法安全推断的歧义；
- 修改超出项目根目录、变更范围或安全策略；
- 删除、覆盖、发布、推送、外部服务写入等不可逆或外部副作用；
- 同一错误重复出现、修复预算耗尽、验证证据缺失或项目状态不一致；
- 发布前的人工确认。

“狂奔已开启”不是“项目已完成”。只有真实验证、交付检查和人工发布确认都满足后，项目才进入完成状态。

### 6.4.7 采纳后的阻塞重算与复合 ID

阶段阻塞必须基于采纳完成后的最新磁盘内容和 manifest 重新计算：

- 核心制品中的稳定 ID 支持业务域复合格式，例如 `REQ-MUSIC-001`、`AC-MUSIC-001`；manifest 必须提取并持久化这些 ID，不能只识别 `REQ-001` / `AC-001`。
- 采纳成功、采纳失败或外部编辑处理完成后，下一次阶段状态事件必须刷新 manifest 并重新计算阶段出口；不得沿用采纳前的 `execution_stage_blockers`。
- 状态事件顺序固定为：先从磁盘刷新 manifest，再调用统一阶段计算函数，最后发送 `project.state` 与 `project.plan.state`；前端不得自行依据旧快照修正 blocker。
- 已满足的 `REQ` / `AC` 出口不得继续出现在 `execution_stage_blockers` 或 `execution_stage_missing`；真实缺失时仍必须保留对应阻塞。
- 侧栏、对话总结和后端阶段状态必须使用同一份重算结果，避免出现“没有发现阻塞”与“本阶段阻塞：REQ / AC”并存。

### 6.4.8 文档图表渲染契约

文档中的 Mermaid 图源和界面预览必须保持同一份真源：

- Markdown 中标记为 ` ```mermaid ` 的代码块必须在文档预览中渲染为 SVG；不能把 Mermaid 源码当普通代码块展示。
- 渲染失败时保留可读的原始 Mermaid 源码，并显示明确的图表错误状态；不能静默丢图或让整篇文档渲染失败。
- 图表渲染必须覆盖文档正文、项目制品预览和对话消息使用的统一 Markdown 渲染入口。
- 部署图、流程图、时序图等只保留 Markdown 图源一份，不把导出的图片作为第二套需要维护的真源。

### 6.4.9 文档导航与阅读区

左侧栏和主工作区职责分离：

- 左侧栏只展示文档入口、文件名、状态和必要的短摘要，不渲染完整文档正文、宽表格或大尺寸 Mermaid 图。
- 点击文档后切换主工作区的“文档阅读”焦点，在主区宽度内渲染 Markdown、表格、代码和 SVG 图表。
- 文档阅读区必须显示当前路径、返回聊天/上一个工作区入口，并允许从文档列表切换其他文件；不通过挤压侧栏宽度解决长内容。
- 文档阅读和聊天、计划审阅、完整计划使用同一主区焦点模型，切换焦点不丢失当前会话与文档选择。
- 窄屏时文档阅读区可以全屏覆盖，但仍不得把完整正文塞回固定宽度的左侧栏。

### 6.4.10 统一阶段状态快照

阶段状态采用一份由后端计算的快照，供侧栏、计划审阅和对话总结共同使用。前端不得根据文档数量、`completeness` 或自己的启发式重新推导“阻塞”。

快照至少包含：

- `execution_stage`：当前阶段；
- `execution_stage_status`：`in_progress`、`blocked` 或 `ready`；
- `execution_stage_blockers`：当前出口缺失、L2 stale、权限失败和真实执行错误；
- `execution_stage_missing`：当前阶段尚未具备的出口项，可用于解释 blocker；
- `execution_stage_warnings`：不阻塞当前阶段的 lint、skeleton、draft 和后续阶段建议。

判定规则：

1. 文档整理中的“尚未生成”属于 `in_progress`，进入 `missing` 或 `warnings`，不得进入 `blockers`。
2. `blockers` 为空时，所有界面统一显示“没有发现阻塞文档”；不得仅因存在 `missing` 或 `warnings` 显示“本阶段阻塞”。
3. `project.state` 与 `project.plan.state` 必须使用同一后端函数和同一字段语义；前端只展示快照。
4. 只有快照状态变化或 blocker 内容变化时，才允许触发新的阻塞/审阅提示。

本节是对齐生产级 agent harness 的第一条运行时契约：状态计算集中、展示降噪、执行门和人看到的状态一致。

## 7. 任务工作方式

每次只围绕一个小批次工作：

1. 读取当前四个核心制品。
2. 选定一个任务，确认需求、设计和验证引用。
3. 先做最小实现。
4. 执行对口验证。
5. 根据结果更新任务和验证证据。
6. 失败就修复或新建任务，不跳过验证继续扩大范围。

需求变化时，先更新上游需求/设计，再调整任务和验证；不在任务列表里偷偷改变产品目标。

## 7.1 第一条真实验收路径

以 `workspace/test` 的 Music Dreamer 为试点，必须先跑通下面的最小路径：

```text
粘贴项目简介
  → 只得到需求归纳
  → 用户确认整理
  → 生成四个核心制品草稿
  → 用户确认设计
  → 只执行一个任务
  → 执行对口验证并记录结果
```

这条路径中任一阶段出现越权、自动推进、无证据完成或失败后盲试，都算链路失败，不能通过增加提示语掩盖。

## 8. 文档策略

- 文档服务于交付，不以“齐全”作为目标。
- 新增文档必须解决一个已经出现的交付问题，并明确它的唯一职责。
- 旧设计可以保留作历史参考，但不能继续作为运行时硬门槛。
- 任何新阶段、新制品、新 Gate，必须先说明它解决的真实阻塞，并通过一次真实项目验证后才能固化。
