# 按天日记记忆（草案 / 未实现）

> **状态：proposal / 草案 · 未实现**  
> 记录时间：2026-10-28（Asia/Shanghai）  
> 真源意图：用户提出的「一个界面承载全部」背后的记忆分层；本文档只固化设计，**不包含任何实现代码**。  
> 配套已决：久远记忆走 Letta / MemGPT 路——核心索引很小，正文按需 `read_file`（见 [MEMORY.md](./MEMORY.md)）。

## 0. 一句话

表面上只有一个会话界面；底下用 **按天日记目录** 管时间线，用 **按项目、按天的会话库** 管进项目时的完整片段，用 **久远记忆** 管跨天仍值得留的硬事实。三套分工，同一事实不双写。

---

## 1. 表面：一个会话界面

用户始终在同一聊天窗说话；不强制先选「会话 / 项目」入口。

底层仍可按会话 / 项目拆上下文与权限（只聊 vs 动手、项目 scope），但那是运行时路由，不是用户要切换的第二套「记忆产品」。

---

## 2. 目录层：按天日记（Day journal directory）

按 **自然日** 一条（或一天一条可展开的目录项）。

### 2.1 表面信息（目录上能看到的）

| 字段 | 内容 | 注意 |
|------|------|------|
| 日期 | 哪一天 | 用户时区（Asia/Shanghai） |
| 聊了什么 | 当天闲聊 / 总览的 **压缩摘要** | 短，可扫 |
| 动过哪些项目 | 项目 **名 / id** 列表 | **只写项目身份，不写改了什么代码** |

目录层禁止贴 diff、文件路径清单或代码级变更说明。

### 2.2 写入时机（建议，未实现）

- **不要**实时双写目录与详情（易抖、易脏）。
- 优先在 **按天收尾** 或 **context 压缩（compact）** 时生成 / 更新目录条。

---

## 3. 某天详情（Day detail）

点进某一天后：

### 3.1 普通对话

- 闲聊时段：**保留**原文，或仅做轻量压缩（仍可回看对话感）。

### 3.2 进项目时段

当这一天里进入过某个项目工作时，该时段在「某天详情」里 **不堆完整项目会话**，只留下：

1. **短压缩提示**：几句话说明「这个项目里大概改了 / 做了什么」——**不到代码层面**（无大段 diff、无逐文件清单）。
2. **稳定链接**：点进去能通到该时段的具体会话内容（见 §4）。

### 3.3 项目提示模板（建议，未实现）

固定三句左右，例如：

1. 做了什么（结果向）
2. 未完成 / 下一步
3. 可点开看完整片段（链接）

避免模型把提示写成小作文。

---

## 4. 项目会话库（Project session store）

链接指向的「具体会话内容」：

- **按项目**保存；
- 项目内再 **按天**归档。

也就是说：完整进项目对话不堆在「全局某天详情」里，而在 `项目 → 某天` 下；日记详情只留短提示 + 链接。

### 4.1 链接稳定性（建议，未实现）

链接应指向稳定坐标，例如：

`project_id + date + segment_id`

**不要**依赖会滚动的消息行号或可变 UI 索引。

### 4.2 落地切片（建议顺序，未实现）

| 切片 | 内容 | 状态 |
|------|------|------|
| **第一刀** | 按天目录 + 进项目时段的短提示与链接（链接可先落到现有 thread / 片段 id） | 草案 |
| **随后** | 完整的「按项目、按天」会话库与浏览面 | 草案 · 后做 |

---

### 4.3 工作记录：什么值得记，记些什么

> **2026-10-29 产品方向；全部未实现。** 为单对话的事后回查补充可追溯工作记录；不新建项目库、不恢复旧 TASKS 队列或自治调度器。物理存储及现有会话、回执的复用方式待核对。

- **判断与生命周期**：明确需要跟踪的工作，开始时建立轻量当前事项；完成、受阻或用户叫停时形成工作记录。受阻、叫停不等于完成。是否值得单独记录拿不准时先不建记录，正常保留对话，待用户要求时从仍可访问的对话和证据整理；普通闲聊、简短概念解释通常不单独记录。无法找回来源时如实说明，不保证对话永久保存。具体自动判断、纠错和保存失败策略待设计。
- **内容**：用户要求、涉及对象、实际结果或停下的位置、实际验证情况和来源；未验证或未记录应如实标明。摘要不默认复制完整工具日志或文件全文，按权限从来源查看详情。候选技术字段包括稳定记录 / 事项 ID、可选项目 ID、时间、状态、会话 / 消息 / 回执坐标及证据引用；schema 待设计。
- **项目与独立事项**：项目是可选归属；修改简历等独立事项不需创建或绑定项目，也需有可追溯身份。续作时结合当前对话和可访问记录识别同一项目或文件，能可靠确定则关联既有对象及历史，并保留新的工作过程；不确定或存在多份候选先问，不只凭同名合并。修改前检查当前状态与权限。
- **稳定来源**：优先复用可靠的会话、消息、回执或工作记录 ID，不依赖可变 UI 位置。没有可靠坐标时说明无法追溯，不编造链接。项目、事项、工作过程与卡片不是同一身份。

**用户确认的部分完成记录（2026-10-29）：** 一个项目下有多项要求时，单项形成明确结果后及时保存该项实际结果和可用证据，不等待项目所有要求结束；该项完成不代表整个项目 / 本轮工作完成。其他要求继续如实显示各自状态，整体结束后再汇总；具体持久化、错误恢复及粒度仍待设计和验证。
### 4.4 保存、查找与隐私

- **保存**：记录默认保留，不因工作结束或卡片收起自动删除；关键结果不能只等日终 / compact，可保存记录或引用已有持久化真源。日记和项目按天视图负责索引 / 链接，不维护互相竞争的完整事实。写入失败、重复回执、中断和恢复的可靠性方案尚待设计，不能承诺尚未落盘的数据已保存或无限期可用。
- **查找**：用户在同一对话中直接问，由 Agent 借助可用工具查有权访问的工作记录、对话及回执，不要求用户自行翻历史或找回卡片。简单问题直接回答并可附来源；需要细节时按需展示记录卡片。大量历史应可检索、分页 / 渐进加载，不铺在主对话里。
- **证据不足**：先回答有证据的部分并说明缺口；需要进一步检查当前文件或历史版本时先与用户沟通，并遵守适用权限。区分当时有依据的事实和现在观察到的状态；缺失、冲突或无权访问时不编造，也不把未找到等同于未发生。
- **隐私和删除**：简历记录默认保存修改摘要及必要文件引用，不复制整份简历正文；摘要和路径也可能含个人信息。用户提出删除记录时，先澄清并说明删除 / 保留范围并取得确认；删除工作摘要不默认删对话或原文件，删原文件需单独明确授权。备份、脱敏、删除后恢复和其他材料的细则尚未设计。

**用户确认记录保存失败处理（2026-10-29）：** 区分实际工作结果与记录保存结果：如实告知已完成的工作与记录保存失败，不因记录失败自动重复修改，也不声称已可靠存档；用户同意后重试保存。消息或进度未持久化时不保证重启后仍可见；幂等写入、失败提示及恢复机制待设计和验证。
**用户确认验证结果的时间与范围（2026-10-29）：** 每次工作记录保留当时实际验证、结果、范围及可用证据；后续修改后不得自动把旧测试通过视为当前通过。回答历史时说明是哪次验证，询问当前状态时若后续未重新验证应如实说明；需要运行测试确认当前状态时先与用户沟通并遵守权限。版本、证据关联及失效判断待设计。
**用户确认历史检索范围（2026-10-29）：** 用户指定对象或时间时优先按指定范围查找；未指定时先查当前对话及相关事项，不足时再扩大到其他可访问历史。Agent 负责检索与回答，不要求用户自行翻记录；多个可能对象时先询问，回答说明依据，不混合不同对象。全过程遵守现有权限，找不到或证据不足如实说明；索引、跨会话访问授权及性能策略待设计。
**用户确认历史与现状不一致（2026-10-29）：** 历史记录与当前文件不一致时，分别陈述有证据的历史记录和当前观察，不将当前文件当作当时样貌，不据不一致断言历史记录有误或猜测修改者 / 时间。用户希望追查时再按权限检查可用历史版本或备份并说明依据；不自动覆盖当前文件以恢复一致。索引、版本与权限细节待设计。
**用户确认历史回答详略（2026-10-29）：** 范围宽且相关记录多时，Agent 默认简要概览最近几次工作及可证实的未完成事项，明确说明时间 / 数量范围，不将部分结果冒充全部历史；用户可继续指定主题或时间展开，细节按需展示带来源的历史卡片。大量结果分批并说明尚有后续；若用户明确要求全部或特定范围，优先遵循其要求。具体默认条数、分页与工具实现待设计。
### 4.5 单对话状态与工作卡片

- **当前工作入口**是有限的当前状态投影，不是历史库。显示进行中、需要确认和未查看的重要结果等；项目与独立事项先看整体概况，点开查看要求，也可直接问 Agent。入口显示和确认交互以 [多项目编排 §10A](./MULTI-PROJECT-ORCHESTRATION.md#10a-单对话中的当前工作与历史回查2026-10-29-设计补充) 为准。
- **看过与收起**：打开结果详情，或针对该结果回复 / 提问，可视为看过；仅出现在屏幕上不算。已完成的结果被看过后等待 **30 分钟**，再从当前工作区自动收起；不删除对话或记录，看过不等于满意或验收。待确认、受阻及未看过的重要结果不因超时悄悄消失。计时持久化、回复指向的可靠判断和纠错待设计。
- **用户确认的多要求项目收起边界（2026-10-29）**：项目仍有进行、需确认或受阻要求时，项目继续留在当前工作概况；单项完成并看过满 30 分钟，不使整个项目消失。已完成要求可在项目详情保留简行；旧对话卡片与记录不删除。待该轮要求均结束、重要结果均已看过且各自经过 30 分钟后，项目才从当前工作区收起；已停止 / 排队及其他混合状态的精确规则仍待设计。
- **用户确认关闭期间计时（2026-10-29）**：30 分钟按看过后的实际经过时间计算，关闭应用不暂停；重开时已超过时间且满足收起条件则从当前工作区收起，保留原对话、卡片和工作记录。未查看的重要结果、待确认或受阻事项不因超时收起；看过时间未可靠保存时不猜测，保守继续显示。计时持久化、系统时钟变更和异常恢复的具体实现待设计。
- **重要更新与重发**：新完成明确要求、需要确认 / 受阻、验证结果产生或改变结论、用户要求重看时，Agent 在对话中重新发送**对应项目自己的完整工作卡片**，不是重新发整批项目；需要确认的操作及影响仍须直接说清。新结果待查看，看过后重新计时 30 分钟。独立事项也可采用同类卡片，具体视觉待定。
- **用户认可的项目卡片内容（2026-10-29）**：项目身份、时间及最新已知状态、各项要求和状态、本次重要变化、实际验证及未验证情况、可展开详情和来源。要求过多时默认展示有限条并明确还有多少，可按需展开；需确认的问题仍由 Agent 在对话说明。视觉细节、限制数量与来源实现待设计。
- **用户确认卡片默认展示数量（2026-10-29）**：每张项目工作卡片默认最多显示 5 条要求，优先展示需确认、受阻、进行中及本次变化；其他要求通过明确的“查看全部 N 项”展开。完整卡片不要求所有要求默认展开，但应可访问该次快照完整状态；旧卡片保持当时快照，不能被后续进度改写。排序冲突、极大量要求、快照持久化和无障碍交互待设计。
- **用户确认独立事项卡片（2026-10-29）**：确实需要跟踪的独立事项可有以事项命名的工作卡片，无需项目归属或“无项目”标签；简单润色等普通对话不强制卡片。独立事项卡片遵循项目卡片相同的重要更新、最多 30 秒合并、快照、查看及完成后 30 分钟收起、记录与回查规则；关联身份、权限和并发仍按独立事项约束。触发 / 展示细节待实现及验收。
- **避免刷屏**：同一项目短时间内的普通重要更新可合并为一张最新完整卡片；需要立即确认或严重受阻时不等待合并，直接说明。默认窗口为 30 秒，详见下条；合并展示不丢弃记录与来源。
- **用户确认卡片合并等待（2026-10-29）**：同一项目的普通重要更新从首个待发送更新起最多等待 30 秒，期间更新合并成一张最新完整卡片；不同项目独立计时，不因持续更新无限延迟。需要立即确认或严重受阻时直接通知，不等待；此等待只作用于卡片发送，不暂停实际工作或推迟保存工作结果。故障恢复、重复发送去重及临界时序待设计。
- **卡片版本**：旧卡片保留在原对话位置，标注时间及当时状态；新卡片展示最新已知状态与变化。当前工作只显示最新状态，用户询问现状时查最新可用来源，并如实说明过期、失联或不确定。
- **历史展示**：结果消息和旧卡片随对话自然滚远。用户以后直接问 Agent；回答简单时无需新卡片，复杂结果或用户要求时可展示有来源的历史摘要，不把历史卡当作实时状态。

**待设计 / 验证**：事项与记录 schema、隐私与存储、持久化及崩溃恢复、计时器与重启、消息归属、合并窗口的故障时序、卡片视觉与独立事项呈现。需定向覆盖五项目多要求加独立简历、未验收、重复操作、千条历史、跨项目隔离、缺失证据 / 权限、保存失败等；当前均未实现或验收。

### 4.6 事项身份、记录与来源关联：候选方案（待用户审核 / 未实现）

> 此节是为进一步讨论提出的**候选逻辑模型**，不是最终 schema、存储选择或实现承诺。复用优先，不新建项目库、旧 TASKS 队列或第二套 Goal 预算；实际复用须先核对现有契约、权限及迁移成本。

#### A. 四层对象及边界

| 对象 | 建议身份与职责 | 边界 |
|------|----------------|------|
| 对话 / 消息 | 复用现有 `conversation_id` 与消息持久化；原始要求及答复是来源之一 | 不能假设每条旧消息已具有可跨重写稳定的 ID；历史可能截断、损坏或无权访问 |
| 事项与要求 | 每次明确要跟踪的事项和具体要求拥有稳定标识；项目为可选归属，同一项目的要求可归组 | 事项身份不授予执行权限；项目、独立文件和显示标题不能以名字自动推断为同一对象 |
| 工作过程 / 结果记录 | 记录一次执行的结果、未完成、验证及证据；同一事项续作关联不同过程，单项要求完成可先记录 | 候选字段参见 §4.3；状态与证据分开，失败 / 停止不变成完成，保存失败不虚报 |
| 对话卡片快照 | 关联对应事项及某次可追溯状态版本，标注生成时刻，展示当时的内容 | 旧快照不随新状态改写；当前工作只读取最新可核验状态；快照不是执行真源 |

#### B. 最小关联例子

```text
会话 C ── 用户原始请求（来源）
          ├─ 项目 A [项目 ID]
          │   └─ 工作事项 W1 [事项 ID]
          │       ├─ 要求 R1：调整页面 ── 结果记录 E1 ── 证据引用
          │       ├─ 要求 R2：修复并测试 ─ 结果记录 E2 ── 验证 / 回执
          │       └─ 卡片 S1 / S2 ── 分别指向各自展示时的状态版本
          └─ 独立事项 W2：修改简历 ── 原文件引用 / 结果记录
```

以上只展示关联，并不要求一个项目只有一个事项，也不要求新建层级文件或数据库。用户修改要求时追加变更并保持原请求；误认归属时标记修正，不抹除已发生事实。跨事项引用须核验来源及各自权限。

#### C. 数据责任与故障边界

1. **权威来源分工**：已有会话消息、执行回执及 Goal 状态各自只证明其记录的内容；工作记录链接证据，不以模型摘要代替证据。Goal Runtime 现有 `last_verification` 是最近一次验收结果，不应被假定为逐要求的完整历史。关联是否需要新增持久层待核对。
2. **写入顺序候选**：从执行结果 / 回执形成记录，记录确认保存后才标为“已存档”；卡片从可核验状态形成快照。执行成功与记录失败要分别报告，失败时不重做修改；不声称会话消息或卡片已经可靠保存。事务、原子性和重试均待实现设计。
3. **幂等与恢复**：用稳定操作 / 过程身份识别重复回执，重复写入不应制造重复结果或覆盖事实；身份生成、提交确认、崩溃窗口、恢复与版本迁移尚未确定。重启后不自动恢复执行，无法确认的状态需提示。
4. **来源检索与权限**：按当前对话到其他可访问历史检索；每项来源校验项目、路径及访问权限。缺失、损坏、权限不足或对象歧义时报告，不编造链接，也不从当前文件断言历史。日志、路径、简历摘要可能包含隐私，保存与检索都需遵守相应权限。
5. **可删除与版本**：快照和索引应能引用具体版本，不依靠 UI 行号；删除范围、备份、索引失效及撤回尚待设计，明确确认前不删原文件或对话。

#### D. 实施前待核对与定向验收

- 核对现有消息 / 回执是否有稳定 ID、`messages.jsonl` 的追加与快照写法、会话历史截断与损坏行为；不能据本草案认定已有满足要求的消息 ID 或数据库。
- 核对 `GoalState` 的单目标 / 最新验证边界、子代理回执与实际持久化、确认请求的单当前态；明确复用位置及兼容策略后再定 schema。
- 定向覆盖部分完成、重复回执、写入失败 / 中途崩溃、旧卡快照、纠错、跨项目与独立事项权限、重启与 30 分钟计时、历史来源缺失以及多确认不串台；不以 UI 概念图或文档设计冒充真实验收。

## 5. 与久远记忆（Letta / MemGPT）的分工

已选久远记忆形态（与现网 MEMORY 三件套中的「久远」一致、并向 Letta/MemGPT 收紧）：

- **核心**：system 里只留很小的 id + summary 索引；
- **正文**：按需 `read_file`（或等价读正文工具）。

| 机制 | 管什么 | 不管什么 |
|------|--------|----------|
| **按天日记** | 时间线：哪天聊了啥、动过哪些项目；进项目时段的短提示与链接 | 跨天仍成立的偏好、约定、硬事实百科 |
| **久远记忆** | 跨天仍值得留的硬事实（偏好、约定、长期背景） | 「哪天改过哪个项目」的流水账 |

### 5.1 不打架规则

- 同一事实 **只升格一次**：该进久远的进久远；日记里可 **链过去**，不两处各写一篇长文。
- 日记是 **何时 / 哪个项目**；久远是 **长期仍为真**。

### 5.2 查找怎么走

| 用户想查 | 优先走 |
|----------|--------|
| 哪天聊过、某项目那天大概做了啥 | **按天日记**（再经链接进项目按天库） |
| 长期偏好、约定、人设级事实 | **久远记忆** |

典型路径：先日记定位时间与项目 → 需要硬事实再读久远。

## 6. 概念图（与用户对齐过的理解）

```text
[ 一个会话界面 ]
        |
        v
[ 目录 · 按天 ]
  · 日期
  · 聊了什么（压缩）
  · 动过哪些项目（仅名/id）

[ 某天详情 ]

另路（不替代日记）：
[ 久远记忆 · 小索引 + 按需正文 ]  <- 跨天硬事实
```

## 7. 主对话确认（草案 / 未实现）

> **状态：proposal · 未实现。** 配合「一个界面承载全部」：后台仍可拆会话/项目/模式，但关键切换与高风险动作应在 **主对话中清楚询问** 并让用户确认，而不是静默改上下文或关键词硬切。

### 7.1 原则

- **意图工具优先**：用分类/意图工具给出「建议动作 + 理由 + 置信度」，再在对话中询问；不靠脆弱关键词硬切。
- **确认后才生效**：用户明确确认后才切换模式 / 进项目 / 接受记忆等；拒绝则保持现状。
- **普通路径少打扰**：普通闲聊、只读查看、常规小范围编辑 → **通常不需额外确认**。

### 7.2 已讨论、应收进对话确认的场景

| 场景 | 对话确认意图（示例） | 备注 |
|------|------------------|------|
| **模式切换** | 「这像要动手改代码。切换到动手？」 | 只聊 ↔ 动手；可附建议 shell（闲聊/项目） |
| **进入 / 切换项目** | 「把当前工作绑到项目 X？ / 切换到目录 Y？」 | 含 `bind_project_dir` 一类能力；同会话换项目需确认 |
| **高风险动作** | 「将执行：… 确认继续？」 | 破坏性命令、不可逆写入等（细则后定） |
| **记忆接受 / 拒绝** | 「建议记住：…」[接受] [拒绝] | 与久远记忆 proposal / 记忆架一致；压缩软沉淀也不自动入库 |
| **双车道同步 / 合入** | 「用稳定刷实验？」/「把实验合入稳定？」 | 脏工作区、分叉、非快进等应在对话确认或同级阻断里说清原因 |

### 7.3 缺口补全（用户未点名、但同一产品原则应覆盖）

| 场景 | 为何需要确认 | 草案倾向 |
|------|----------|----------|
| **解绑 / 关闭当前项目** | 离开项目 scope 会改权限与上下文，静默做容易「还以为在项目里」 | 确认后再清绑定 / 退回只聊或未绑状态 |
| **跨天续跑长 Goal** | Goal Runtime 预算跨 segment 不重置；隔天「接着做」是显式恢复，不是自动续 | 对话确认摘要：Goal 状态、剩余预算、上次停在哪 → [继续] [先暂停] |
| **外部账号动作** | 发邮件、发帖、下单/支付等会离开本机、有外部可见后果 | 必须对话确认；展示收件人/正文或订单摘要；未批准不发送 |
| **大爆破半径改动** | 整仓重构、批量改名、大规模删除等比「改一个按钮颜色」危险得多 | 对话确认说明影响范围（路径数/模块）；可要求二次确认 |
| **静默失败后的自动重试** | 自动连试可能放大损坏或刷爆外部 API | 失败可见；是否重试由用户确认或明确策略，避免无限静默重试 |

### 7.4 通常不需额外确认

- 普通聊天、解释、只读查文件 / 文档
- 已在动手+已绑项目内的 **常规、小范围** 编辑（用户已处于该工作上下文）
- 纯展示类 UI（打开记忆架查看、看双车道状态）——**真正执行** 刷实验 / 合入 / 接受记忆时再确认

### 7.5 与按天日记 / 久远记忆的关系

- 对话中的确认是 **当下决策面**；日记是 **事后时间线**；久远是 **跨天硬事实**。
- 「接受记忆」对话确认通过后，才写入久远库；日记目录仍按 §2 建议在收尾/压缩时更新，不在每次对话确认时双写。

### 7.6 明确未实现

- 无统一确认交互实现、无意图工具→对话确认的接线、无上表场景的产品文案定稿。
- 本节只锁定 **该确认 / 不该确认** 的产品边界，供后续想法继续叠。
