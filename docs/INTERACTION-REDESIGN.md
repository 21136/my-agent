# 现代项目交互重设计

> 版本 0.2.0 · 2026-08-24  
> 状态：**项目上下文栏与决策条方案已定 · UI-6001 实施中**  
> 关联：[PRODUCTION-PROJECT-MVP.md](./PRODUCTION-PROJECT-MVP.md)、[DESKTOP-TEXTBOOK-FLOW.md](./DESKTOP-TEXTBOOK-FLOW.md)、[PROJECT-SIDEBAR.md](./PROJECT-SIDEBAR.md)、[TASKS.md](./TASKS.md)

## 1. 背景与判断

当前项目已经具备项目绑定、四个核心制品、阶段权限、计划审阅、任务授权和验证证据等能力，但用户体验仍然像“把内部控制台搬到了桌面上”。问题不在颜色或圆角，而在交互模型：系统把内部状态、实现术语和中间产物直接暴露给用户，用户必须自己理解流程、判断提示真假，再决定下一步点什么。

本设计将 Desktop 从“状态驱动的管理面板”调整为“目标驱动的项目工作台”：

```text
用户说目标 → 系统整理上下文 → 系统后台准备 → 只在需要决策时询问 → 用户确认 → 系统连续执行 → 给出结果与下一步
```

现有生产项目 MVP 的阶段和硬门槛继续有效；本设计只改变呈现方式、打断策略和用户心智模型，不改变项目文件真源、权限边界或验证要求。

## 2. 设计目标与非目标

### 2.1 目标

1. 用户打开项目后，5 秒内知道当前项目、当前目标、当前进度和下一步动作。
2. 用户不需要理解 `requirements`、`documentation`、`blocker`、`plan review` 等内部术语，也能完成项目主链路。
3. 普通状态更新、文档生成和质量建议不打断工作；只有需要用户决策或确实无法继续时才打断。
4. 所有重要信息在一个主工作区形成连续叙事：目标、文档、任务、代码变更、验证结果相互可追踪。
5. 侧栏从“内容仓库”变成“项目态势摘要”，详细内容在主区按需打开。
6. 失败、阻塞和待完善建议有明确区别，系统不会让同一个问题同时显示为“没有阻塞”和“本阶段阻塞”。

### 2.2 非目标

- 不新增一套项目状态机；继续使用后端统一阶段快照和现有权限闸门。
- 不把四个核心制品扩展成强制七文件模板。
- 不取消设计确认、任务授权、测试证据和发布人工确认。
- 不把所有工作自动化；涉及范围、方案取舍、风险接受和发布的决策仍由用户完成。
- 不在本轮重做 Terminal、Pet 壳或通用聊天能力。

## 3. 核心心智模型

### 3.1 用户只需要理解四件事

| 用户看到的概念 | 用户要回答的问题 | 系统内部映射 |
|---|---|---|
| **目标** | 我现在要把什么做出来？ | 当前项目目标、当前批次、当前任务 |
| **进度** | 做到哪了？ | 阶段快照、任务状态、工具生命周期、验证证据 |
| **需要我决定** | 现在必须由我拍板什么？ | 范围确认、设计确认、方案提案、风险接受、发布确认 |
| **结果** | 做成了吗？哪里能查看？ | 文件变更、任务证据、验证结果、发布检查 |

内部阶段只作为辅助信息显示在详情中。默认文案使用“正在了解需求”“正在整理项目方案”“正在实现当前任务”“正在验证结果”等用户语言。

### 3.2 目标卡是主叙事锚点

每个项目主区顶部只有一个当前目标上下文，包含：

- 目标标题或项目名称；
- 当前批次或当前任务；
- 状态：进行中、等你决定、已完成、被阻塞或失败；
- 当前阶段和任务进度；
- 一句下一步说明；
- 必要时由独立决策条承载主按钮，按钮文案直接描述动作，例如“确认范围”“查看方案”“开始实现”“查看验证结果”。

上下文栏不显示项目原始 Markdown、任务清单或一组并列的内部按钮，也不同时要求用户关闭多个提示。

### 3.3 项目上下文栏与独立决策条

目标信息和决策信息分层展示，避免用一张大卡片同时解释项目、任务和阻塞：

```text
项目名 · 正在整理项目文档 · 2/4 文档 · 进行中

范围需要确认
确认内容：第一轮交付范围
影响：确认后进入设计阶段
[查看范围] [确认范围]
```

- **项目上下文栏**固定为单行或两行紧凑区域，只展示项目名、用户可理解的当前阶段、进度和状态徽标；不截断或渲染 `project_summary` 原文。
- **决策条**只在没有用户选择就不能安全继续、存在真实阻塞或需要验收时出现；它必须说明“决定什么、影响什么、确认后去哪一步”，并提供一个主动作。
- 决策条必须提供与确认动作分离的详情入口；范围确认显示“查看范围”并打开 `SCOPE.md` 主区全文，方案确认显示“查看方案”并进入方案详情，详情页提供“返回聊天”。
- **聊天焦点**始终保留完整对话区和输入框；上下文栏与决策条不能挤压对话到摘要或几行文字。
- 完整目标、范围、详细描述、任务队列和文档正文通过项目概览、任务或文档焦点查看；不塞进上下文栏。
- 没有决策或真实阻塞时，不渲染空的决策条，也不显示灰掉的确认按钮。

### 3.4 Harness 规则与用户交互分层

生产流程中的阶段、Gate、证据、审查、归档和权限是 **Harness 对 LLM 的约束**，不是要求用户逐项操作的界面流程。用户不应该为了让系统继续运行而理解或关闭这些内部状态。

系统采用两层契约：

| 层 | 负责什么 | 默认是否展示给用户 |
|---|---|---|
| Harness 层 | 阶段权限、工具白名单、任务授权、验证 Gate、审查判定、归档和状态机 | 否；只作为系统事实和诊断详情 |
| 用户层 | 当前目标、正在做什么、需要用户决定什么、结果和下一步 | 是；使用用户语言和单一主动作 |

映射规则：

- Harness 可以静默拦截越权工具，但用户只看到“当前还不能做什么、原因是什么、如何继续”；
- Harness 可以收集 warning、证据和审查结果，但用户只在这些信息改变下一步决策时看到汇总；
- Harness 可以归档任务并计算阶段，但用户看到的是“正在验证”或“待发布验收”，而不是内部归档、M1、M2 或 Gate 名称；
- 只有真实需要用户授权、确认风险或人工验收时，才生成用户决策条；普通状态变化不能生成“关闭/确认”打断。

任何新内部字段进入 UI 前，必须回答：它是否改变用户现在的选择？如果不改变，就留在 Harness 状态、过程详情或开发诊断中。

## 4. 用户主流程

### 4.1 新项目或空项目

```text
打开或新建项目
  ↓
输入目标/背景/用户场景
  ↓
系统展示「我理解的是……」
  ↓
用户确认理解，或补充修改
  ↓
系统后台整理 PROJECT / DESIGN / TASKS / VERIFY 草稿
  ↓
主区展示「方案已准备好，等你确认」
```

用户只提供需求时，系统保持只读，不运行工具、不写业务代码。只有用户明确进入项目整理并且项目已绑定后，才进入文档整理批次。

### 4.2 文档整理批次

四个核心制品的生成是一个批次，不是四个独立的交互任务：

- 主区显示一个连续进度：“正在整理项目文档 2/4”；
- 左栏只显示四个制品的状态点，不自动展开正文；
- 普通缺项、lint 建议和计划搭档观察收集到批次摘要；
- 写入失败、权限失败、阶段越权和真实执行错误立即停下并说明原因；
- 批次结束后一次性显示“文档整理完成，发现 N 项待完善”，可选择查看或稍后处理。

### 4.3 设计确认与实现

```text
文档已准备 → 用户查看方案摘要 → 用户确认本批次方案
  → 系统显示可执行任务 → 用户选择一个任务开始
  → 系统连续执行代码/测试 → 完成后展示验证结果
```

确认动作必须说明影响范围，不使用无上下文的“确认”“采纳”按钮。推荐文案：

- `确认这份方案`：确认当前 DESIGN 与本批次任务映射；
- `开始实现 T-001`：授权一个明确任务；
- `接受风险并继续`：接受系统已经明确列出的风险；
- `确认发布`：人工确认版本发布检查。

用户确认后，系统可以连续执行当前任务需要的工具；不因每个文件写入、每次状态刷新或每个普通 warning 再次询问。

### 4.4 完成与下一步

任务完成后，主区优先展示结果和证据：改了什么、验证了什么、结果在哪里。下一步默认为“查看变更”或“开始下一个任务”，但不自动启动下一任务。

### 4.5 任务队列清空不等于项目完成

任务列表中的勾选只记录一个任务已经从当前开放队列收口；即使用户连续勾选了全部任务，也只能进入“任务已清空 · 待验证”。它不能直接把项目标记为完成，也不能跳过验证、交付审查、发布检查或人工验收。

项目状态必须按以下顺序推进：

```text
任务已清空 → 验证证据 → 交付审查 → 发布检查 → 用户确认发布 → 项目完成
```

在发布阶段且收到人工验收回执之前，目标卡、顶栏、项目列表和提示文案禁止使用“项目已完成”或“全部完成”；应明确告诉用户当前还缺哪一道门。

## 5. 页面信息架构

### 5.1 总体布局

```text
┌──────────────────────────────────────────────────────────┐
│ 顶栏：项目名 · 当前目标 · 会话 · 设置                     │
├───────────────┬──────────────────────────────────────────┤
│ 项目态势侧栏   │ 主工作区                                 │
│               │ 目标卡 / 当前动作                         │
│ 当前进度      │ 对话、方案、文档、变更、验证结果           │
│ 当前任务      │                                          │
│ 需要我决定     │                                          │
│ 异常与风险     │                                          │
│               │                                          │
│ [项目] [文档]  │                                          │
│ [任务] [验证]  │                                          │
└───────────────┴──────────────────────────────────────────┘
```

### 5.2 顶栏

顶栏只保留全局操作：

- 当前项目切换；
- 新建会话；
- 当前目标的简短标题；
- 设置、帮助和停止当前运行。

不在顶栏堆叠阶段、阻塞、计划、服务等内部状态。

### 5.3 侧栏：项目态势

侧栏常驻内容按固定顺序排列：

1. **当前目标**：一句话目标和当前任务；
2. **进度**：一条主进度，不同时展示两套完成/未完成计数；
3. **需要我决定**：最多一张最高优先级决策卡；
4. **异常与风险**：只展示真实阻塞、失败和未处理风险；
5. **快捷入口**：项目、文档、任务、验证以图标或短标签进入主区。

以下内容默认不常驻：完整 `TASKS.md`、工具调用清单、Services 列表、变更日志全文、每个文档的长摘要。它们在主区或覆盖面板中按需查看。

### 5.4 主工作区焦点

主区只能有一个当前焦点：

| 焦点 | 主内容 | 返回入口 |
|---|---|---|
| **聊天** | 用户目标、系统解释、执行过程和结果 | 默认焦点 |
| **方案** | 方案摘要、取舍、影响范围、确认动作 | 返回聊天 |
| **文档** | 选中文档的完整正文、表格和图表 | 返回聊天/文档列表 |
| **任务** | 当前任务及开放队列、依赖、证据 | 返回聊天 |
| **验证** | 验证项、命令结果、失败原因、发布检查 | 返回聊天 |

侧栏点击入口只负责切换主区焦点，不在窄栏内展开完整正文。聊天状态在焦点切换时保留。

### 5.5 任务工作区（修订）

“查看任务”不应该是目标卡下方的几行摘要，也不应该把完整 Markdown 计划直接塞进聊天主区。成熟项目工具把任务列表作为**一等工作视图**：列表负责浏览、排序和定位，详情负责查看和操作，二者有清晰的层级和独立滚动区域。

本项目采用桌面优先的任务工作区：

- 进入任务后，主区切换到独立的“任务”焦点，不破坏聊天历史；
- 顶部保留项目目标、进度和返回聊天，任务列表拥有自己的滚动容器；
- 列表默认展示完整开放任务队列，按当前任务、待开始、已完成或阶段分组；不截断成几行，也不把长文档当列表；
- 点击任务后，在同一工作区右侧打开任务详情，展示交付物、依赖、验收和证据；窄窗口降级为详情抽屉；
- 每个开放任务详情都必须提供“开始实现”动作；该动作完成后，后端将项目推进到实现阶段，主区上下文栏切换为当前任务，而不是停留在“查看任务”；
- 如果设计文档尚未确认，任务详情不得显示可执行的“开始实现”；主区必须先显示“确认设计”，确认成功后才开放任务授权。
- 列表和详情都支持返回、键盘上下切换和稳定的当前任务定位；
- 目标卡只负责告诉用户“为什么做、现在到哪、下一步是什么”，不承担任务清单职责。

### 5.6 主区焦点与垂直空间

目标卡收敛为项目上下文栏，不是主内容区：

- 上下文栏固定为紧凑高度，只展示项目名、阶段、进度和状态；不展示原始 Markdown 长摘要；
- **聊天焦点**：上下文栏（必要时加决策条）+ 完整对话区，聊天区占据剩余主空间；
- **任务焦点**：上下文栏 + 任务工作区，聊天消息区和输入框隐藏，任务工作区占据剩余主空间；
- 任务焦点提供“返回聊天”，不能让任务列表和聊天区同时争夺垂直空间；
- 任何焦点下都不允许出现“上下文栏占满上半屏、主内容只剩几行”的布局。

### 5.7 目标卡的最终形态（UI-6009）

目标信息仍然需要，但“目标卡”不再作为一个独立的大容器保留。它容易把目标说明、阶段状态、任务摘要和操作按钮重新堆在一起，导致用户误以为必须先阅读或处理一张流程卡才能继续。

因此，默认主路径采用**项目上下文栏**：

- 只保留 `项目名 · 当前目标 · 当前进展 · 一个下一步动作`；
- 当前目标使用一句可读的业务目标，过长时截断，但支持通过项目详情或聊天查看完整内容；
- 当前进展只显示一个用户可理解的口径，例如“实现登录流程”或“3/8 个任务”；
- 普通状态不展示 Gate、Phase、profile、证据、审查 verdict、归档等 Harness 内部信息；
- 需要用户决定时，才在上下文栏下方出现独立决策条，明确“要决定什么、会影响什么、点击后做什么”；
- 没有用户动作时不保留空白卡片，也不重复展示已经在聊天或任务工作区出现的说明；
- 上下文栏是只读定位，不承担目标编辑、任务浏览、文档阅读或验证详情。

这样保留了目标的方向感，同时把垂直空间还给聊天和工作区。目标详情的入口应是项目详情或聊天中的明确链接，而不是把默认首页变成目标说明页。

## 6. 自动执行与用户决策边界

### 6.1 系统自动完成

- 读取当前项目上下文和已有核心制品；
- 归纳需求、识别缺失信息并生成草稿；
- 在文档整理批次内生成或更新四个核心制品；
- 刷新 manifest、阶段快照、进度摘要和普通 warning；
- 根据已确认任务连续调用允许的工具；
- 去重同一批次内的提示；
- 在失败后停止并保留结构化错误和证据。

这些动作属于 Harness 内部连续处理，不应被拆成“请用户确认阶段”“请用户关闭提示”的连续操作。

### 6.2 必须由用户决定

- 项目目标和范围是否正确；
- 方案取舍是否接受；
- 是否开始某一个具体任务；
- 是否接受明确列出的风险；
- 是否确认发布。

“系统发现一个建议”不等于“用户必须现在审阅”。建议只有在会改变项目文件、任务或执行计划时，才生成可操作提案。

确认按钮只能在后端权威回执成功后更新状态；请求失败时保留原决策条，显示失败原因和重试入口，不得乐观推进到“准备开始下一步”。

### 6.3 打断规则

系统打断前必须满足至少一个条件：

1. 没有用户决定就无法安全继续；
2. 发生真实错误，继续执行会扩大影响；
3. 用户授权已过期或项目边界发生变化；
4. 当前批次已完成，需要用户决定是否进入下一段。

其余信息进入状态摘要、过程区或稍后汇总，不弹关闭式提示。

## 7. 提醒与状态分级

### 7.1 四级提醒

| 级别 | 用户看到的语义 | 展示方式 | 是否打断 |
|---|---|---|---|
| **进度** | 正在做什么、已经完成多少 | 上下文栏/过程区 | 否 |
| **待完善** | 可以改进，但不妨碍当前运行 | 侧栏徽标/批次摘要 | 否 |
| **需要决定** | 没有你的选择不能安全继续 | 独立决策条 | 是 |
| **失败/阻塞** | 当前无法继续，原因和恢复动作 | 独立决策条+侧栏异常 | 是 |

### 7.2 术语映射

| 内部事实 | 默认用户文案 | 禁止单独展示的文案 |
|---|---|---|
| `status=in_progress` | 正在整理/正在实现/正在验证 | “阶段状态处理中” |
| `warnings` | 待完善，不影响当前运行 | “本阶段阻塞” |
| `blockers` | 需要处理：原因 | “blocker” |
| `suggestions` 带有效 action | 有一个方案需要你确认 | “计划审阅队列” |
| 无有效提案 | 当前没有需要确认的方案 | “待审阅” |
| `verification` 失败 | 验证未通过：查看失败原因 | “证据门失败” |

内部 ID、阶段名和状态字段只在详情或开发诊断中展示。

### 7.3 去重与生命周期

提醒以 `project + batch + fingerprint` 去重。一个提醒的生命周期是：出现、被处理或被关闭、内容改变后重新出现。关闭不会改变事实，也不会把建议伪装成已解决。

“关闭”是当前提示的展示动作，不是确认、采纳、验收或发布动作。关闭任务变更提示后，不得触发自动确认；只有用户点击“确认”或倒计时自然结束且用户没有关闭提示时，才允许确认当前变更。变更内容指纹发生变化后，提示可以重新出现。

## 8. 六种关键状态

### 8.1 空项目

文案：“这个项目还没有目标。告诉我你想做什么。”

主动作只有“输入项目目标”。不显示灰掉的“确认范围”、空任务计数或无意义的阶段按钮。

### 8.2 处理中

上下文栏显示具体动词和进度，例如“正在整理项目文档 · 2/4”。过程区可以查看细节，但默认不展开长日志。用户可以继续补充信息，也可以停止运行。

### 8.3 等你决定

决策条显示一个明确问题、对象和影响范围，例如“方案已准备好：是否按这个范围开始实现？”。主区保留完整聊天内容，非关键建议折叠。

### 8.4 被阻塞

必须同时展示三件事：

- 阻塞事实：缺什么或哪里失败；
- 影响：因此无法进行哪一步；
- 恢复动作：补充信息、重试、修改文档或返回上一步。

没有真实 blocker 时，界面不展示“本阶段阻塞”。待完善建议只能显示为“可选改进”。

### 8.5 失败

失败不是阻塞的同义词。失败卡保留原始错误、已执行动作、是否产生文件变化和推荐下一步；不自动显示成功，不要求用户先关闭一堆历史错误。

### 8.6 已完成

展示结果摘要、变更文件、验证证据和下一步选项。完成只代表当前任务或当前批次完成，不自动代表项目发布；“确认发布”必须单独由用户执行。

“任务已清空”属于批次状态，不属于项目完成状态。任务清空后应显示验证入口和剩余门槛；只有发布检查通过并记录人工验收，才显示“项目已完成”。

## 9. 文档、任务和验证的呈现

### 9.1 文档

左栏只显示四个核心制品的名称、状态和更新时间；主区显示全文。文档状态使用“未开始、整理中、可查看、待完善、已确认”这类用户语言。

### 9.2 任务

主区任务列表默认按“当前任务、下一步、其余开放任务、已完成”分组。每个任务至少显示交付物、验收方式和当前状态。只有用户主动打开完整队列时，才展示所有任务和依赖关系。

### 9.3 验证

验证区围绕“证明什么”组织，而不是围绕工具名组织。每项显示验收目标、实际命令或人工步骤、结果和证据位置。失败项直接关联到恢复动作。

## 10. 调研结论与设计依据

本轮核对了成熟工具的官方交互说明：

| 产品 | 观察到的做法 | 对本项目的启发 |
|---|---|---|
| [Linear Display options](https://linear.app/docs/display-options) | Issue view 是完整列表/看板视图，支持分组、排序、手动排序、子任务和显示字段；列表不是卡片摘要 | 任务需要独立列表视图，并把“看什么”与“怎么操作”分开 |
| [Linear UI redesign](https://linear.app/now/how-we-redesigned-the-linear-ui) | 用 list、board、timeline、split、fullscreen 等结构承载不同工作；通过层级和独立面板降低噪声 | 不要让一个目标卡同时承载目标、任务和完整计划 |
| [GitHub Projects table layout](https://docs.github.com/en/issues/planning-and-tracking-with-projects/customizing-views-in-your-project/customizing-the-table-layout) | 项目项组成可配置表格，支持分组、筛选、排序、字段显隐和行重排 | 任务应能完整浏览，列表操作应有明确的工作区边界 |
| [VS Code Tasks](https://code.visualstudio.com/docs/editor/tasks) | 任务通过工作区任务选择器启动，执行输出和 Problems 视图分离 | 任务选择、任务详情和执行结果不要混成一段长文本 |

因此，当前“查看任务”按钮不应继续沿用“卡片下方摘要”或“完整计划长卷”两种极端。下一版 UI-6001 应先增加 `mainFocus=tasks` 的独立任务工作区，再决定任务详情的右侧面板与窄屏抽屉。

## 11. 从现有 UI 到新 UI 的迁移策略

采用渐进迁移，不一次推翻现有工作流：

### M0：统一文案与状态入口

- 保留现有 WS、阶段快照和权限模型；
- 为目标卡、侧栏、主区定义统一 view model；
- 删除或隐藏重复状态文案；
- 将 `warnings`、`suggestions`、`blockers` 按新分级呈现。

### M1：任务工作区优先

- “查看任务”进入独立任务焦点，不再打开 Markdown 长卷；
- 首屏展示完整开放任务列表，当前任务固定高亮；
- 任务列表与任务详情使用独立滚动和返回路径；
- 现有 `plan_full` 作为兼容入口保留，默认主路径迁移到任务工作区。

### M2：侧栏收敛

- 侧栏只保留目标、进度、决策、异常；
- Services、本回合工具列表和完整文档内容改为折叠或主区入口；
- 所有完整阅读内容进入主区焦点；
- 旧兼容节点保留事件绑定，但不再作为可见卡片渲染。

### M3：主区焦点统一

- 聊天、方案、文档、任务、验证共享一个焦点状态；
- 点击侧栏入口不丢失聊天滚动位置和会话状态；
- 所有“确认/采纳/开始”按钮改为带对象和影响范围的动作文案。

### M4：执行连续性与人工验收

- 文档批次内普通提示后台收集；
- 同一批次只显示一次汇总；
- 用户确认后当前任务连续执行；
- 增加基于真实用户路径的 Desktop 手工验收。

迁移期间旧术语可以在开发诊断或详情面板保留，但不得出现在默认主路径。

## 12. 验收总则

除任务专属验收外，现代交互版本必须满足：

1. 首屏能说清“当前项目、当前目标、下一步”。
2. 用户不需要关闭重复的普通提示才能继续工作。
3. 没有真实阻塞时，侧栏、主区和对话不会出现矛盾的阻塞结论。
4. 完整文档、任务队列和工具细节不挤占侧栏主视线。
5. 每一个会阻止继续的动作都说明原因、影响和恢复方式。
6. 用户确认一个动作后，系统连续执行该动作范围内的工作，不逐文件或逐 warning 打断。
7. 任务完成仍以真实验证证据为准，视觉上的“完成”不能绕过生产项目 MVP 的硬门槛。
