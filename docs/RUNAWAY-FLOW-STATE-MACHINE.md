# 狂奔流程状态机与恢复协议

> 版本：0.1.0 · 2026-08-26  
> 状态：实现基线

本文定义项目“狂奔模式”的运行时契约。狂奔是 Harness 驱动的连续交付作业，不是把更多内部提示展示给用户，也不是让 LLM 自行决定项目阶段。

当前实现进度：R1～R6 已落地；R2 的跨进程运行租约和更完整的生产观测仍可继续增强。

## 1. 用户契约

用户在已绑定项目中显式开启狂奔并提交一次目标后，Harness 自动完成：

```text
准备 → 文档/设计出口 → 选择可执行任务 → 实现 → 验证 → 修复或下一任务 → 发布等待
```

默认不要求用户确认计划、任务、阶段或“继续”。用户只在以下情况介入：

- 需求、范围或验收标准无法安全推断；
- 操作超出项目授权范围，或涉及删除、发布、推送和外部写入；
- 验证问题重复、修复预算耗尽、状态不一致或运行资源耗尽；
- 验证通过后的最终人工发布确认。

用户界面只展示“正在做什么、已完成什么、为什么暂停、用户需要决定什么”，不展示内部状态名、工具白名单或计划审阅卡。

## 2. 状态模型

持久化字段 `project_runaway_checkpoint` 使用以下状态：

| 状态 | 含义 | 自动动作 |
|---|---|---|
| `idle` | 已授权但尚未启动 | 启动作业 |
| `preparing` | 正在整理需求、文档和设计出口 | 生成或采纳项目内部计划 |
| `implementing` | 正在执行一个任务 | 只允许当前任务范围内操作 |
| `verifying` | 所有当前任务已完成，正在验证 | 必须执行对口命令并记录证据 |
| `repairing` | 验证失败且仍可修复 | 同范围修复后重新验证 |
| `release_wait` | 验证和交付检查通过 | 等待用户人工发布确认 |
| `paused` | 需要用户或外部条件介入 | 不得自行继续 |
| `completed` | 用户已确认发布 | 关闭本次狂奔作业 |

状态切换只能由 Harness 的统一转移函数完成。任何异常、进程重启或连接断开都必须保留当前状态，不能用空 checkpoint 表示“仍在运行”。

## 3. 状态转移

```text
idle
  → preparing
  → implementing
  → verifying
  → repairing ─────┐
       └───────────┘
  → release_wait → completed
  → paused → preparing | implementing | verifying
```

### 3.1 进入条件

- `preparing`：项目已绑定，目标已写入当前会话，狂奔授权有效。
- `implementing`：四个核心制品具备当前阶段出口，任务存在、依赖已满足，并且当前任务被 Harness 绑定。
- `verifying`：任务队列没有开放任务，或当前任务已完成；验证命令和验收项可解析。
- `repairing`：真实验证已执行并失败，失败指纹未重复，修复预算未耗尽。
- `release_wait`：验证命令成功、交付审查通过、关键制品为 current。
- `completed`：用户人工发布确认已经写入并绑定当前 `RELEASE.md` revision。

### 3.2 失败规则

- 参数格式错误最多自动修正一次。
- 权限、路径越界、用户拒绝、外部网络和不可逆动作立即进入 `paused`。
- 同一验证失败指纹再次出现立即进入 `paused`。
- 自动修复最多 3 次；预算耗尽进入 `paused`。
- 工具总轮次或 24 小时运行预算耗尽进入 `paused`，并记录原因。

暂停必须写入 `project_runaway_paused_reason`、最近错误和错误指纹，并向用户发送一条可执行的自然语言说明。不能只返回普通 `turn.end` 或“运行中”。

### 3.3 阶段出口的可修复缺口

`documentation` 阶段的制品缺少必要 ID、章节或验收映射时，属于 Harness 可修复的阶段缺口，不属于用户阻塞。狂奔应在当前项目范围内续接文档生成/修复，重新运行设计确认检查；只有文档修复工具失败、权限或路径越界、同一缺口重复出现，或运行预算耗尽时才进入 `paused`。用户界面显示自动修复进展，不要求用户确认普通文档闸门。

## 4. 检查点与恢复

检查点至少包含：

```json
{
  "checkpoint": "implementing",
  "task_id": "T-001",
  "task_fingerprint": "…",
  "task_done_baseline": 2,
  "tool_rounds": 18,
  "repair_count": 0,
  "last_verification": "",
  "last_error": "",
  "last_error_fingerprint": "",
  "paused_reason": "",
  "updated_at": "…"
}
```

检查点写入必须发生在任务切换、验证开始/结束、修复开始/结束、暂停和发布确认之前。进程重启后：

1. 加载项目和会话；
2. 获取同一项目的运行租约，避免重复作业；
3. 按 checkpoint 恢复到对应阶段；
4. 重新读取磁盘、manifest、TASKS 和验证证据；
5. 只有入口条件仍满足时才继续，否则进入 `paused`。

关闭开关必须取消正在运行的作业并落 `paused`，不能仅修改一个布尔值。重新开启不能清除历史错误、任务指纹或修复预算，除非用户明确执行“重置本次运行”并且磁盘状态已发生变化。

## 5. 任务选择

Harness 不再简单选择第一条未完成任务。任务选择必须过滤：

- 当前任务未完成；
- 所有 `depends_on` 任务已完成；
- 任务引用的需求、设计和验证 ID 仍为 current；
- 任务不属于已暂停或已关闭范围。

没有可执行任务但仍有开放任务时，进入 `paused`，原因必须列出未满足的依赖。

## 6. 验证与交付出口

验证由 Harness 驱动，不以 LLM 口头声明或单次 `deliverable_review` 调用代替：

1. 读取 `VERIFY.md` 和项目验收命令；
2. 实际执行对口测试/构建/验收命令；
3. 将命令、退出码、关键输出摘要、时间和关联 `V-*` / `AC-*` 写入验证证据；
4. 再运行只读交付审查，合并硬证据与审查结论；
5. 通过才进入 `release_wait`，失败才进入 `repairing` 或 `paused`。

### 6.1 R4 证据协议

每次狂奔验收都写入项目 `.plan-agent/runaway-verification.json`，至少包含：

```json
{
  "project_id": "demo",
  "command": "python tests/acceptance.py",
  "exit_code": 0,
  "expected_exit_code": 0,
  "passed": true,
  "verify_ids": ["V-001"],
  "ac_ids": ["AC-001"],
  "recorded_at": "…",
  "evidence_fingerprint": "…"
}
```

`release_wait` 必须同时满足：验收命令真实执行且退出码符合预期、证据记录属于当前项目、`deliverable_review` 为 `pass` 且无 blocker。仅有任务全完成或 LLM 自述“已验证”都不能进入发布等待。

任务队列清空只能触发 `verifying`，不能触发“项目已完成”。最终完成必须满足真实验证、交付检查和人工发布确认。

## 7. R5 用户界面契约

Harness 的内部状态机服务于自动执行，不应变成用户必须学习或逐项确认的操作流程。用户界面以“当前进展”为主叙事，默认不展示 checkpoint、内部阶段名、工具门、计划审阅、任务总数/完成数或 LLM 的调度术语。

### 7.1 用户可见的信息

主界面只保留以下四类信息：

- 正在做什么：例如“正在整理项目资料”“正在实现当前功能”“正在验证交付结果”；
- 已完成什么：例如“功能已实现，验证通过”；
- 是否真实阻塞：只在确实无法自动继续时显示原因、影响和下一步；
- 用户需要决定什么：仅保留范围、不可逆操作和最终发布确认。

“狂奔”开启后，计划、任务选择、修复、验证和阶段切换均由 Harness 自动完成；提案采纳不再进入用户确认队列。狂奔运行中的普通进展不提供“确认计划”“计划审阅”“选择任务”等按钮。

### 7.2 详情与状态分层

摘要只负责回答“现在怎么样”，详细内容通过用户主动打开的详情面板查看。详情面板可以展示任务、文档、验证证据和变更，但不在主进展卡中展开长文本，也不把内部字段名作为标题。

状态文案与动作遵循以下映射：

| 内部情况 | 用户看到 | 用户动作 |
|---|---|---|
| 自动执行中 | 正在实现/验证/修复 | 查看过程、停止运行 |
| 等待真实外部条件 | 暂时无法继续 + 原因 | 查看原因、处理阻塞后重试 |
| 验收和交付检查通过 | 已验证，等待你确认发布 | 确认发布 |
| 人工发布确认完成 | 已完成 | 无需动作 |

任务队列清空、文档尚未生成、某个内部阶段尚未闭合，都不能单独显示为“项目阻塞”或“项目完成”。只有统一状态机写入的暂停原因才可进入阻塞展示。

### 7.3 普通模式边界

普通模式可以保留必要的人工确认，但确认应描述用户要承担的业务决策，不得暴露“计划门”“阶段出口”等实现概念。计划和任务详情仍通过显式入口查看，不在侧栏持续弹出审阅提示。

### 7.4 系统提示词覆盖优先级

当 `project_runaway_enabled=true` 且当前会话已绑定项目时，系统提示词必须明确声明狂奔覆盖普通项目纪律；否则模型会被旧的“确认计划”“一项一停”和“等待用户继续”规则拉回人工流程。

- 狂奔覆盖：计划提案采纳、阶段推进、任务切换、项目内安全写入和本地测试确认。
- 狂奔仍受限：网络访问、宿主目录、密钥/敏感文件、删除、发布、Git 提交和推送必须暂停或请求人工决定。
- 狂奔失败出口：重复验证失败、修复预算耗尽、运行预算耗尽、状态不一致和真实外部阻塞进入 `paused`。
- 普通模式原规则只在狂奔未开启时生效；提示词不能同时输出互相矛盾的“自动继续”和“等待确认”。

该覆盖既要出现在静态项目提示词，也要出现在动态 project overlay；动态 overlay 优先输出当前狂奔状态和安全边界，不能再输出“用户须项目确认后才可写源码”。

## 8. 实施顺序

| 批次 | 内容 | 完成标准 |
|---|---|---|
| R1 | 统一 checkpoint、转移和暂停原因 | 所有入口/异常使用同一状态语义 |
| R2 | 狂奔作业启动、取消、恢复和运行租约 | 开关、重启、断连不产生假运行或重复运行 |
| R3 | 阶段出口和依赖感知任务选择 | 不跳过前置条件，不以第一条开放任务代替调度 |
| R4 | Harness 驱动验证和证据落盘 | 没有真实证据不能进入发布等待（已落地） |
| R5 | 用户界面收敛 | 只显示自然语言状态和真实决策，不显示内部流程门（本节） |
| R6 | 可靠性与长跑演练 | 跨进程不重复执行，重启/崩溃可恢复，预算耗尽可解释暂停 |

## 9. 已落地行为

- `runaway_flow.py` 统一检查点、合法转移、暂停原因和任务指纹，并兼容旧的 `implementation` / `verification` 值。
- `SessionMeta` 持久化当前任务指纹；关闭狂奔会取消正在执行的回合并写入 `paused`，重新开启会保留错误、修复次数和任务上下文。
- WebSocket 会在会话恢复后续接活动检查点；R6 已将项目租约扩展为跨进程原子抢占、心跳和过期接管。
- `TASKS.md` 支持 `depends_on: T-*`，狂奔调度只选择依赖已完成的开放任务；没有可执行任务时记录暂停原因。
- R4 已落地：验收命令真实执行，证据写入 `.plan-agent/runaway-verification.json`；没有硬证据或交付审查通过不能进入发布等待。
- R5 契约已定义：内部 Harness 状态只驱动自动执行，主界面只呈现进展、真实阻塞和必要决策；详细内容通过显式详情入口查看。
- R6 契约已定义：租约、预算、故障矩阵和长跑演练标准见 `docs/RUNAWAY-R6-RELIABILITY.md`。
- R6 已落地：项目级租约使用原子文件抢占、心跳、TTL、进程存活检查和 token 安全释放；租约与恢复演练见 `agent-core/runaway_lease.py` 及其测试。
