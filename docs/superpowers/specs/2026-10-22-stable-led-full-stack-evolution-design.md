# 稳定端驱动的全栈演化：详细设计

- 日期：2026-10-22，Asia/Shanghai。
- 版本：设计 0.1。2026-10-22 用户确认设计并要求制定实施计划；这是设计确认，不是独立审查通过。未授权功能实现、稳定端改写或发布。
- 范围：在稳定工作台中持续开发、试运行和最终采用下一代 my-agent，覆盖 UI、工具、agent-core、依赖、原生桌面和存储架构。
- 配套契约：[运行、场景与采用协议](./2026-10-22-stable-led-full-stack-evolution-contracts.md)。本文决定产品和安全边界；配套契约细化字段和操作，不另建任务体系。
- 产品依据：[PRODUCTION-PROJECT-MVP](../../PRODUCTION-PROJECT-MVP.md)。详细设计按仓库现有 specs 约定保存；实现获准后接入现有任务与验证制品，不创建第二套项目流程。
- 本轮实际写入只在 sandbox 文档中；所有“应”“必须”和接口名称均为设计要求，不表示已经实现。

## 1. 要解决的问题及非目标

用户说“这里窄一点”“增加一个能用的工具”“替换当前调度架构”，应当都是同一个开发入口。系统负责把需求连接到源码修改、候选运行、真实观察和修复；用户不必先管理分支、端口或实验会话。

核心产品契约：**开发会话留在可用的稳定系统；被开发的实验系统可以失败、更换内部架构和重启，但不能夺走该会话的诊断与修复能力。**

本设计不是开放任意代码后宣称绝对安全，也不是让 Agent 无人确认地发布自己。第一版不做云端多租户、自建包仓库、通用 VM 平台、全功能 IDE、无限递归自举或多任务并行改同一实验树。不承诺宿主 OS/虚拟化漏洞下的绝对隔离。保护边界之外的风险必须明示。

## 4. 总体架构：小控制底座，完整候选系统

```text
用户 / 稳定工作台（唯一主会话、原有聊天与附件链）
        │                                  ▲
稳定开发 Agent                              │ 任务关联事件、结果、场景
        │ 窄接口、经过权限检查                │
        ▼                                  │
演化监督器 EvolutionSupervisor（固定发布版本，不含 LLM）
  ├─ WorkspaceBroker：受控补丁、基线、快照和变更归属
  ├─ CandidateRunner：环境、构建、启动、停止、超时和资源边界
  ├─ EvidenceLedger：版本绑定、事件、宿主观察和交付状态
  └─ CapabilityBroker：受限模型推理、下载/网络、产物交换
        │                        │
        ▼                        ▼
实验源码 sandbox          隔离环境内的完整候选
                           UI / agent-core / tools / native / data
```

### 4.1 稳定开发 Host

继续使用稳定端当前的 Agent、会话和任务系统。不为演化再建一套聊天数据库。Agent 可读取被授权的源文件、提交补丁、请求候选构建与用例、查看结构化结果。**请求增加新工具，不会把该新工具加载到稳定 Agent 的工具注册器。**稳定 Agent 通过候选试验观察其效果。

演化任务中的执行策略必须阻止借现有 run_command、run_service、run_evolved 或 interactive_terminal 在宿主执行候选代码。相关工作委派到 Runner。普通项目原有执行权限不是候选代码执行的旁路授权。

稳定内核在执行候选修复时仍使用自己的已知可用工具和依赖。候选可提供建议补丁，但写入仍由可信 Broker 验证、执行。

补丁的 before-hash 检查与写入必须受同一文件排他操作保护，不能只有 Broker 进程内锁。单写租约不阻止外部编辑器；文件系统/原生锁无法提供所需排他语义时返回 scope_conflict，不冒险覆盖。写入中断保留前像、intent 与恢复记录，不能把文件级写入宣传为已验证的断电原子事务。实施需分别验证 exFAT 与 NTFS 的文件操作行为。

### 4.2 演化监督器

一个独立、无模型决策的本地进程，使用**已安装并固定版本**的发布产物，不能从正在修改的 sandbox 导入模块。它拥有候选进程句柄、操作日志、取消令牌和恢复记录。稳定 sidecar 重启时可重连查询，而不是再启动一份候选。

稳定主进程与监督器通信；稳定 Agent 通过服务端适配器调用。稳定浏览器 preload 只暴露具体方法，不暴露通用 IPC、命令或任意路径操作。授权同时校验会话、任务、调用方、操作和当前版本。候选通道不允许访问稳定控制通道。

首版只支持一个监督器实例和一个 sandbox 写租约。客户端断线不是授权继续无限执行：当前受限操作可在期限内结束；新的模型调用、外部副作用和采用立即冻结。应用重启后根据日志恢复观察，不自动恢复未知操作。

### 4.3 恢复 Launcher 与控制底座升级

普通候选试跑不重启稳定 Host。稳定 Host/监督器升级则是单独的代际交接：当前代构建下一代，下一代先在副本和只读检查模式运行，确认后才交接数据写租约。

恢复 Launcher 是独立的小发布入口，只负责读取 last-known-good 发行描述、启动已知版本或选择已准备的下一代。候选无权写该描述。监督器自己更新时也不覆盖正在使用的发行目录。Launcher 本体更新须单独发行、用户确认，不由普通演化任务原位修改。 冷启动还必须核对采用 journal、数据 schema/revision 和写租约；若上次切换中断或旧发行与当前数据不兼容，只启动维护/只读恢复入口，不因 last-known-good 存在就让旧 Host 写真实数据。

稳定旧入口尚无这些机制，不能声称新底座已经在工作。所有实现先在 sandbox 验证；首次启用需要单独批准将底座发布到稳定端。禁止为“证明稳定控制”先私自修改当前根目录。

## 5. 工作区、依赖与数据布局

设计中的逻辑位置：

| 位置 | 写入者 | 内容与约束 |
| --- | --- | --- |
| 实验源码 F:/my-agent-main/.worktrees/sandbox | 用户、受控补丁 Broker | 唯一实验源码编辑树；保留已有 dirty；不直接用作受验收运行目录 |
| trusted_state_root/evolution | 固定版本监督器 | 事件、授权、版本清单、接收后的证据、恢复记录；不映射给候选 |
| trusted_release_root/releases/<release_id> | 发行操作 | 控制底座与已批准运行版本；候选只获得必要的运行副本 |
| run_input/<candidate_id> | 监督器准备 | 筛选源码快照、锁文件、批准的运行时/依赖缓存；进入保护环境时只读映射 |
| run_exchange/<instance_id> | 宿主和候选各有独立消息子目录 | 仅当前实例的消息和产物暂存；不能作为可信日志，也不能暴露其父目录 |
| guest_workspace / candidate_profile | 候选 | 构建输出、包安装、临时文件、测试会话、迁移数据副本；全部可丢弃 |

trusted_state_root 与 trusted_release_root 在正式部署时必须位于经过能力检查的 NTFS 私有目录，且不位于候选可写映射内。建议解析到应用现有 per-user 数据位置下的专用子目录；首次创建这些 workspace 外位置需要明确的发布/路径授权。**本轮不创建它们。** sandbox 中的原型状态仅是开发夹具，不自动获得“可信安装”资格。

不靠 chmod/只读文件属性保护 F: 上的控制文件。即使改用 NTFS，同用户任意宿主代码也不是强隔离，所以仍须区分执行等级。

### 5.1 源码快照

- 用显式源文件清单，包含构建所需的已跟踪文件和已确认的未跟踪源文件；默认排除 .git、data、.env、凭据、日志、缓存、artifacts、.venv 和 node_modules。
- 测试数据只从明确的 fixture 或用户批准的导出加入；不能把整个工作区打包后再尝试删秘密。
- 运行配置由固定 schema 导出非敏感字段，不直接打包原配置文件。选定源码/配置还须做秘密暴露检查；发现疑似凭据或无法确认敏感等级时停止输入准备，先脱敏或请用户决定。字段名/文件名过滤不能宣称能识别所有未知秘密。
- 文件相对路径规范化，拒绝越界、大小写冲突、设备名、链接/reparse point、重复归档条目；字节不改行尾。捕获中发生变化则重试，仍变化就要求停止编辑后再捕获。
- source_snapshot_id 由规范化清单及文件字节 hash 决定；HEAD 和 dirty/staged 状态只作出处。已有改动与本任务改动分开记录。
- 候选只从捕获后的副本构建。启动前原树又变化，不会让旧副本“变新”；UI 提示当前试验不是最新源码，并另起候选版本。
- 编辑用 live_dev 与验收用 sealed_build 分开。HMR 的场景仅绑定一次页面 generation，不能直接用于最终发行采用。

### 5.2 依赖与构建

Python 使用候选独立环境，不借稳定 .venv；Node 使用候选锁文件和独立安装，不借稳定 node_modules。宿主 .venv 仅用于可信控制代码的验证，不运行候选 import。

安装、postinstall、构建插件、测试脚本都视为候选代码。保护模式中在 guest 内执行。下载缓存按实际哈希和来源验证，只读提供；不在宿主安装包来“预热”。使用网络下载须独立授予下载范围和字节预算；首版离线 guest 通过受限下载 Broker 获得已批准包或运行时归档。

锁文件缺失或变更必须记录解析结果并让用户知悉依赖变更；不能悄悄重解稳定依赖。native ABI、OS/架构、运行时版本均进入 build_fingerprint。任何目标平台重建产生新的产物身份，旧构建验收不得直接沿用。

### 5.3 数据

主会话和任务留在稳定端。候选 trial session 是附属试验，其 candidate_session_id 不替代主 conversation_id。默认使用空数据或 fixtures；用户数据必须按授权字段导出、脱敏和版本化。不拷贝会话锁、在线凭据或整个真实 data。

候选使用独立数据库、userData、缓存、日志和端口；不共享真实数据写锁。数据格式替换需提供 export/import/schema inspection 适配能力或明确不支持迁移；不得因框架更换强行要求复用当前存储类。

## 6. 两种执行等级，不能混叫安全沙箱

### 6.1 local_managed：本地受管试跑

用于经过用户明确授权的可信候选，本机独立进程、依赖、数据和受控生命周期。记录权限暴露、环境白名单与稳定文件基线。禁止默认继承全部 process.env，禁止自动以管理员运行。

但同用户进程、任意安装脚本和共享宿主网络仍可能影响宿主；读写检查及前后指纹只提供防护/检测，不提供强制隔离。UI 显示“本地试跑：可能影响本机”；用户未接受此风险就不执行。此模式可证明功能，不满足“稳定环境受到强保护”的总体验收。

### 6.2 protected_guest：受保护试跑（目标安全等级）

Windows 首个后端选择 **Windows Sandbox guest**，不是只用一个受限工作目录。使用前实际探测 OS 支持、功能可用、运行时、窗口操作、交换目录和隔离负向用例；功能未启用则返回 isolation_unavailable，不安装、不启用系统功能、不自动降级。Windows Sandbox 的文件映射与网络配置能力见 [S2][S3]；这是后端选择，不是已通过的可行性证明。

配置决策：

1. 宿主只映射精确的 run_input（只读）和当前 run_exchange（可写），不映射仓库根、真实 data、用户目录、.git、控制日志或凭据。
2. 候选先把只读输入复制到 guest 私有盘，再安装、编译、运行；无宿主稳定进程访问凭据。
3. 显式禁用 guest 网络、剪贴板、打印机、音视频输入重定向；启用 ProtectedClient；vGPU 默认关闭。因兼容性需放宽时重新列出暴露面并取得授权，不静默修改。
4. 模型推理由宿主 CapabilityBroker 代发；候选只提交有上限的请求，拿不到 API key。网络下载同理。真实局域网联调不属于首版保护配置；需要独立能力评估。
5. 交换目录是敌对输入：只收 schema 校验后的数据与普通文件；限定大小、数量、频率和生存期；拒绝链接/重解析、路径、脚本自动执行和任意宿主命令。
6. 对 guest 退出、消息洪泛、磁盘阈值和构建超时停止试验。初始配置见契约；宿主预警/停止不是 exFAT 磁盘硬配额，也不承诺资源耗尽绝不影响宿主。
7. 不承诺跨 guest 重启保留环境；重复构建可利用经过验证的只读缓存，但不能把可写旧 guest 状态当作可复现依赖。

若该后端无法满足项目真实窗口/模型/构建需求，应记录具体失败条件，单独调整后端设计；不能宣布完成、也不以普通进程替代其保护声明。

### 6.3 可信开发 Agent 的边界

保护模式隔离的是候选代码。稳定开发 Agent 仍是拥有受限操作权限的可信主体，不能借控制接口任意改稳定文件。它也必须经 WorkspaceBroker 的范围和 CAS 校验；候选文本、页面内容和测试日志不能扩张授权。该设计不等于对已被攻陷的稳定控制端提供安全保证。

## 7. 统一操作流与稳定主会话

### 7.1 自然语言开发入口

1. 用户在现有会话提出目标；普通项目/问答不会自动进入演化。
2. 系统识别为本产品演化，记录 evolution_id、主会话、目标范围、验收行为和副作用授权。一次确认覆盖明确范围内的常规编辑/构建/重试；只有权限、数据、联网预算或发行风险变更时再问。
3. 获取 sandbox 单写租约，记录稳定与候选基线。已有 dirty 不清理、归属不明不接管。
4. 稳定 Agent 修改候选源码；Broker 使用 expected_before_hash 防止覆盖外部编辑。
5. 建快照、准备独立环境、构建并启动候选。每步失败都把日志带回原会话。
6. 运行真实用例，用户在预览或候选窗口观察。Agent 根据同一现场修复，产生下一版候选。
7. 展示完成项、未通过项、diff 与风险；用户验收后另行决定是否采用。

开发 Agent 的 run_id 每回合可变，evolution_id 跨回合持续。候选的 runtime_run_id 不进入稳定 Agent 的当前执行状态。UI 的取消当前回合与停止候选是不同操作：取消回合停止其尚未完成的受控工作；已授权的观察窗口可保留，但不再自动发生模型/网络副作用。

### 7.2 不做第二套试验聊天

候选模型 trial 返回的消息作为带来源的试验记录呈现。用户选择“在候选中试用”时，可在候选原生 UI 内交互；它属于候选，不承担主任务确认、稳定发布权限和恢复。

同一稳定会话中，Agent 能同时知道“我在修改候选”“这条结果来自哪一候选”“用户验收的是哪个版本”。不按会话标题猜 lane，不按相同 id 合并两边权威历史。

## 8. 场景驱动预览：不是仅增加截图按钮

### 8.1 默认界面

复用现有壳预览位置，不新建聊天面板、不在聊天区加覆盖层。主内容是候选页面/表面；一级动作固定为“选择元素”“标注”“发送给 Agent”。保留原会话消息草稿、附件和任务引用。版本/隔离状态用短标签；分支、端口、构建日志放过程详情；“采用版本”在验收结果中。

发送动作调用现有 user.message/附件处理链，附服务端签发的 scene_id，不允许候选直接伪造用户消息或传宿主文件路径。发送成功先持久化消息和场景关联，再清除标注草稿；重试按 message_id 去重。模型不支持图像时明确只传结构化场景，标注 image_not_consumed，不能声称模型看过截图。

### 8.2 两类表面与真实原生变更

- **web_surface**：候选 Web 页面，可在稳定 WebContentsView 使用固定的只读场景桥。不能载入候选 preload，也不向其暴露稳定 myAgentDesktop 全量 API。缺候选服务就显示失败，不回落到稳定页面。
- **native_surface**：涉及 main/preload、IPC、原生模块、系统集成或真实桌面功能时，启动候选独立 Electron 和 profile，使用候选自己的 main/preload。首版通过专用候选窗口（保护模式为 guest 窗口）完成真实交互；稳定端显示关联的截图、状态和反馈入口，不声称已经完成无缝远程嵌入。
- protected_guest 首版网络关闭，guest 页面不能作为普通 localhost URL 塞进稳定预览。以 guest 窗口内页面为可操作现场，通过消息交换回传场景。这一交互差异必须可见，后续远程表面是独立增强项，不阻塞内核演化正确性。
- 候选 UI 无场景桥时仍可收视口截图和区域标注，element_unavailable；不能伪造 DOM 选择能力。不可访问 iframe/closed shadow root 明确降级为区域，不静默选中父页面元素。

Electron 的 renderer 沙箱与上下文隔离只是页面桥的一部分，不能代替对原生主进程的 OS 隔离；官方限制见 [S4][S5]。

### 8.3 场景与复核

场景记录当前 route（敏感参数剔除）、viewport、DPR/zoom、滚动位置、元素语义定位候选、边界框、选区或标注、当前视口截图及 source/build/instance/generation 身份。不要收整个 DOM、所有输入值或隐藏内容。密码、token、cookie、localStorage 和表单敏感值默认不采集。 字段排除不等于截图像素已脱敏：固定捕获桥需遮罩已识别敏感区域，保留脱敏策略和失败标记；无法确认时不自动向外部模型发送图片，提供用户本地查看、区域裁剪或明确的数据披露确认。guest 自报脱敏不升级为宿主独立保证。

场景冻结后再编辑标注意见，不让后续导航悄悄改变其对象。截图有 actual_capture、用户附图等来源等级；只有实际 capture 的图可描述为当时现场。guest 来源不自动获得宿主独立观察等级。

修改后产生新实例或页面 generation。恢复请求引用原 scene_id 和新目标身份：恢复可访问路由、视口和滚动；再以稳定 key、role/name、结构路径、文本摘要等定位。返回 exact / approximate / missing / inaccessible 四种结果。多个匹配要让用户选择；不能悄悄选第一个。approximate/missing 时保留原图对照并要求重新选点，不宣称同一元素复核成功。

## 9. 工具新增与内核架构替换

### 9.1 工具新增

候选自行决定工具实现形式和注册机制；当前工具注册器只作为 legacy_adapter。完整用例必须观察：

```text
候选发现/注册工具
→ 候选模型请求包含可用能力
→ 实际模型返回工具调用
→ 候选分发器执行新实现
→ 外部可观察结果
→ 候选把工具结果送回模型并形成回应
```

试验工具不得修改真实数据或向外发消息来证明成功。优先在候选目录产生带随机 case_nonce 的结果文件，宿主安全接收后核验格式、内容与 hash。模型 Broker 记录 provider request id 和 tool_call id；候选上报的 dispatcher trace 是补充，不单独构成成功。

若供应商 API 或授权不可用，结论停在发现/直接执行已验证、真实模型调用未验证。不能通过伪造模型回复、拦截 API 或打印 PASS 补齐。

### 9.2 架构替换

候选入口用启动描述和版本适配器连接监督器，不要求继续提供旧 Python 类、当前 WebSocket 协议或 run_evolved。外部只要求最小身份/状态/日志契约；agent.trial、scene.capture、storage.export 是按用例协商的可选能力。

验证分三层：

1. 新路径确实参与请求：版本化 trace/实现摘要，并检查该实现位于本次源码清单中；这些属于候选内部路径证据。
2. 行为可外部观察：给出该改动特有的输入/输出、持久化结果或调度顺序，宿主按真实结果判定。
3. 旧路径没有悄悄兜底：在候选中禁用旧入口或配置成调用即失败，目标用例仍成功；保留负向用例输出。

三层结合证明该用例使用新路径，不将其扩张为所有路径已迁移或对恶意候选的不可伪造证明。无法关闭旧路径时明确列出残留，不标“架构替换完成”。

### 9.3 权限不是工具描述的一部分

新工具不能通过声明 manifest、输出文字、DOM 标注或注册请求获得宿主文件/网络权限。候选内执行使用 guest 权限；需宿主资源则提出 capability 请求，由已有用户授权和预算裁定。无通用 host.exec、任意 host.read/write 或任意 IPC 转发能力。

## 10. 版本、协议和证据

版本绑定链：evolution_id → source_snapshot_id → build_fingerprint → candidate_id → instance_id → case_id / scene_id。详见配套契约。

监督器是操作日志唯一写入者。会话只持有 evolution_id 和摘要投影，不复制事务真源。每条证据区分 supervisor_observed、broker_observed、guest_reported、candidate_reported、human_confirmed；不能因同一个 JSON 中 ok=true 就提升来源。

端口打开只用于传输发现。身份握手必须与本次启动句柄、私有 boot_nonce、快照和产物匹配；握手是关联，不证明候选诚实。非本任务 listener 既不复用、不停止，也不清理其锁文件。

新旧实例晚到事件可存档但不能更新当前状态。源码变化使旧证据对“当前版”失效，不删除历史。任何授权、采用请求或场景恢复都要重新比较身份和状态 revision，拒绝 TOCTOU 式误用旧确认。

状态拆为候选生命周期、用例 verdict、源码交付、运行采用、数据迁移五个轴。独立审查、安全结果另列；不重用旧 self_change accepted 作为总体批准。

## 11. 故障、取消和恢复

| 故障 | 必须行为 | 禁止行为 |
| --- | --- | --- |
| 依赖安装/构建失败 | 记录命令、环境、退出码和限量日志，回原会话修源码 | 借稳定依赖、删除稳定 node_modules、只改提示为成功 |
| 候选启动失败/崩溃 | 标记该 instance 失败，收集日志，稳定 Agent 继续可用 | 切换开发会话到坏实例、自动显示稳定页冒充候选 |
| 候选失联 | 先 timeout 标记；只停止已拥有的句柄/guest | 按端口杀进程、按旧 PID 杀新进程 |
| 稳定 Agent 重启 | 重连监督器、读取事务、恢复摘要；未知外部副作用等待核实 | 重新发出消息/模型请求/采用操作碰碰运气 |
| 监督器崩溃 | Launcher 重启已知版本；核对进程所有权和 journal，无法确认就 quarantine | 扫描端口抢占服务、把残留进程认作新实例 |
| 整个工作台退出 | 停止 owned 候选；异常退出后启动审计孤儿资源 | 自动重启无限工作或自动发布 |
| 外部编辑同一路径 | CAS 拒绝，展示差异并重新合并 | 覆盖、reset、checkout、回滚整个工作树 |
| 日志或磁盘预算超限 | 限流并停止候选；保留已接收的短摘要 | 无限缓存、自动删真实日志/备份腾空间 |
| 用户取消 | 撤销后续能力授权，停止当前受控操作并等待终态回执 | 把停止请求已发送说成进程已停止 |
| 未知采用/迁移结果 | 保持稳定旧指针或进入维护恢复，核实 journal | 宣称已回滚、自动丢弃新数据 |

同一源码快照的启动失败不无限自动重启。首版自动重启次数为 0，允许用户或稳定 Agent 在查看原因后发起新的显式 retry 操作；同一 operation_id 网络重试只返回已有结果，不重启一遍。

文件恢复只能针对本任务拥有且当前 hash 等于本任务最后写入值的文件逐项 CAS 恢复，保留外部改动。失败恢复不必恢复实验源码原样，优先让稳定端继续诊断；不要把有价值的失败现场销毁。

## 12. 采用：源码、程序与数据分别交接

### 12.1 准备采用而不是自动发布

prepare_adoption 生成绑定 candidate_id、当前稳定基线、变更路径和风险的计划。用户看到：改了什么、验证到哪里、哪些未过、是否重启、是否迁移数据、能如何退回。合入、安装、运行采用与数据迁移都须在确认描述中有明确范围；“继续设计/测试”不构成这些授权。

已有 sandbox 不属于单次任务的改动，不能随整支分支自动交付。prepare 阶段列出 owned/pre-existing/unrelated 三类路径；若选择整支合入，要求用户另外确认完整范围，并重新验证合入后的实际树。默认不自动 add 整个 product、不 commit、不 stash、不推送、不解决冲突。

### 12.2 源码合入

需要明确的 Git 授权和稳定工作区条件。稳定 dirty 有冲突就停止；不自动清理或隐藏。合并冲突不得用统一 ours/theirs 解决。源码合入完成只记录 source_delivery=merged，不自动重启正在工作的稳定系统。 本仓库的正式稳定采用仍必须完成 Git merge 或 PR 的实际合并；把源码、程序和数据拆开记账不是跳过合入规则。只切 URL 或运行指针不算晋升稳定。

若稳定仍直接从可变源码树运行，合入可能使后续 lazy import 混用版本；因此在合入前必须完成固定运行发行包的启动切换，或者安排稳定停机并明确恢复点。不得宣称“进程没重启就肯定不受源码合入影响”。

合入后 sandbox 同步是独立源码操作：用户批准、检查 dirty 和祖先关系、解决冲突、验证实际树；不使用静默偏向任一侧的策略。

### 12.3 运行采用

受验收的产物按内容身份发布。若变更了目标平台、依赖、打包方式或实际代码，则是新 build，需要相应验证。guest 内跑通的未打包源码不自动等于宿主发行包可用。

正式 activate_release 的前置条件包含源码已合入且实际合入树与待采用产物对应；有额外源码差异必须重建并重验。未合入可以暂存发行包或继续试用，不能将其标为稳定采用。

Launcher 写入 prepared 发行记录；新 Host 先在数据副本进行健康/功能检查，不能拿真实数据写租约。确认及停机窗口到来后：旧 Host 排空有副作用的任务 → 锁定数据写入 → 核对基线未变 → 执行已批准迁移 → 新 Host 接管唯一写租约 → 原子切换 active 并保持旧 last-known-good → 观察窗口验收 → 通过后才推进 last-known-good。每步有幂等 operation_id 和落盘记录；观察期失败仍指向旧已知版本的恢复记录，并单独核对数据兼容性。

新旧版本可并行只读观察，但不得双写同一真实数据。没有可靠交接适配器就阻断采用，不靠两个 sidecar 都显示 ready 判成功。

### 12.4 数据迁移及回退边界

迁移计划包含源/目标 schema、输入快照 hash、导出/导入命令、校验规则、兼容性、停机需求、回退能力。先对授权副本演练；采用时暂停写入，再取最终一致快照并核对/重跑。原始副本保留。

- 新版本尚未写入真实数据：检查后可回旧程序和旧数据指针。
- 已有新写入且存在验证通过的逆向迁移：按批准计划回退并核对数据。
- 已有新写入、无安全逆向迁移：停止写入进入维护，不自动恢复旧快照丢弃新数据；用户选择导出/修复/明确接受损失后才能进一步处理。

“恢复旧程序”与“数据无损恢复”是不同结论。外部发信、付款、部署等不可逆副作用首版试验不授权，也不随进程回退而声称撤销。

## 14. 分阶段交付，不把平台搭建当成果

本文是总设计；实施计划按下面可拒绝、可独立验收的交付切片分别制定。每片都接回同一稳定主会话，不建设孤立的演示控制台。

| 顺序 | 可交付结果 | 不可省的真实证据 |
| --- | --- | --- |
| A：稳定修复闭环 | 原会话编辑候选、构建、启动、失败后继续修复；固定监督器和身份链 | 隔离 fixture 故障注入后，在同一主会话修复并重试成功；稳定来源未变 |
| B：执行保护 | Windows Sandbox 后端、私有输入/交换、模型 Broker、负向隔离探针 | 实际拒绝越界宿主文件/真实数据/凭据/稳定进程能力；不可用时确实阻断 |
| C：真实工具与内核替换 | 一次真实模型新工具调用；一次旧路径禁用后的新内核行为 | provider 调用链、随机 nonce 结果和外部观察；两种运行内核不混用 |
| D：共享现场 | 页面选择/标注/发送/同位置复核；原生候选窗口关联 | 真实截图、当前视口/route/元素和新版本定位结果，不是伪 preload |
| E：受控采用 | 固定发行包、源码合入与数据交接解耦、Launcher 恢复 | 副本迁移、唯一写租约、故障回退、不可逆场景明确阻断 |

A 可先使用经过用户授权的本地受管 fixture 证明编排，但安全总体验收必须等 B；不能用 A 的运行成功替代 B。若用户不授权 local_managed，则 A 的真实执行依赖 B，不能绕过。原生桌面改动在 D 之前也可以用独立窗口验证，只是不提前声称现场交互已闭环。

首个端到端验收用例使用**新建的隔离试验夹具**，不臆造生产缺陷：在候选新增一个诊断工具，让真实模型调用；替换一条调度路径；在候选副本注入启动失败；回原会话修复重试；再复核现场。夹具和故障注入的创建/执行边界在实施时单独确认，本文不创建。

## 16. 设计决策与剩余验证点

已在本草案作出的默认决策：稳定主会话不换 lane；独立监督器；候选内部协议可替换；sealed 快照验收；保护模式优先 Windows Sandbox；本地模式单独风险授权；native 用独立窗口先验收；源码/运行/数据采用解耦；稳定 dirty 不自动处理。

这些是设计选择，不是技术探针通过。实现前必须取得以下事实，失败时停止相关切片而非填假结果：

- 此机器 Windows Sandbox 的实际可用性、guest 内 Electron/Python/Node 运行及交换通道可用性；未启用时是否批准启用属于用户决定。
- 保护配置下文件 mailbox 的延迟/吞吐是否足够模型流与场景；首版不承诺视频流或低延迟远程控制。
- 候选对现有实际模型 API 的结构化工具调用支持和所需预算授权。
- 固定发行包、NTFS 私有安装位置、数据写租约和 Launcher 首次部署的批准与真实恢复结果。

不把上述待验证事实写成空白接口；相应错误、阻断行为和验收用例已明确。详细实施计划须在用户评审本文后逐片制定。
