# 单对话工作记录：第一阶段技术方案与验证计划

> **状态：候选方案 / 待审核，未实现。** 本文是第一阶段的技术方案与定向验证计划，不授权实现、启动服务、调用真实模型或改动 Git 状态。实现前须确认运行位置、存储与隐私边界并将待核对项收敛为具体接口。

**Goal:** 在一个对话内，顺序处理一个项目事项与一个独立事项，保存可追溯的要求、结果及验证边界，并能在当前会话回查，缺失来源时诚实报告。

**Architecture:** 保留现有 Session、消息、权限和 Goal Runtime；新增薄的事项 / 结果记录与只读查询能力作为候选，不作为执行调度器或新项目库。桌面卡片和多项目并发不在本阶段；确认和取消沿现有主链。

**Tech Stack:** 现有 Python agent-core、Windows 优先仓库 `.venv`、pytest；存储和暴露接口需完成下列核对后决定，不引入新依赖作为前提。

**Spec:** [DAY-JOURNAL-MEMORY §4.3–4.6](../../DAY-JOURNAL-MEMORY.md)；[MULTI-PROJECT-ORCHESTRATION §10A](../../MULTI-PROJECT-ORCHESTRATION.md)。

## 0. 现有事实与兼容边界（源码只读核对）

- `agent-core/session.py`：`Session.append_message` 可追加消息；`Session.save` 在完整加载后可重写消息快照；`session_history_event` 的 UI 数据由 user / assistant 消息过滤构造、可截断；不能使用显示行号或字节偏移作为长期稳定身份。
- `agent-core/goal_runtime.py`：动手回合旁路保存 `goal-state.json`，预算与 `last_verification` 不是逐要求历史；现有默认 repair_limit 为 3，但验收失败计数不等价于本方案设计的修复轮数。
- `agent-core/subagent.py`：现有 Runner 定位只读，隔离消息不持久化；不可将临时 overlay 当作唯一证据。
- `agent-core/tools/logging.py`：已有 `evolve_log.jsonl` 和 tool-call 元数据，经过参数清理且不保存完整文件正文；不可当作完整工作结果或绕过原权限的检索库。
- `agent-core/tools/executor.py`：`read_file` / `grep` 读取其他会话路径时进入确认判定。本阶段只做当前会话回查；未来跨会话检索必须经现有确认 / 权限链，不靠内部索引绕过。
- `desktop/src/shells/chat-state.ts` 存在当前确认状态及旧确认处理；本阶段不改变或声称支持多个并发确认。
- 此清单只是源码阅读，不表示运行、端到端或生产验收通过。

### 0.1 补充核对与推荐方向（2026-10-29；仍待设计审核）

1. **消息来源**：`Session._append_message_line` 是普通 JSONL 追加；`_write_messages_snapshot` 会整体重写；`_build_chat_history_from_messages` 返回角色、文本和可选图片，未在该投影中提供稳定消息 ID，且过滤、去重、截断。因此不能以 UI 行号、文件偏移或文本相同作为唯一可靠来源。后续新消息稳定 ID 是否以兼容字段实现、是否影响模型 payload 及历史还原须专项设计；旧消息无可信 ID 时如实标注不可稳定定位，不改写旧对话补造身份。
2. **回执来源**：`EvolveLog.log_tool_call` 记录经清理的调用元数据，`log_subagent_run` 记录 kind / tool_rounds / paths 等，不等于完整执行结果；部分大型工具结果可能有 output_path，但不能假设每次都有或永久存在。`GoalState.last_verification` 只表达最新一次验收。建议从实际受控执行结果建立有限证据引用，标记来源 / 范围 / 可用性，缺失时不编造；不把日志当作授权数据库或逐项完整回执。
3. **侧车优先作为候选**：第一阶段建议比较会话目录下独立、版本化结构化侧车与扩展现有 Session 消息；倾向侧车是为了不改变模型消息格式和旧聊天展示，但它不是已定方案。侧车必须复用项目会话目录约束和受保护路径策略；现有 `atomic_write_text` 对单文件采用临时文件替换并可备份，但不提供跨文件事务、并发写锁或断电后持久性保证，不能据此承诺无损。
4. **备份与隐私**：`backup_session_files` 当前只复制 `meta.json`、`messages.jsonl`、`goal.md`；新增侧车不自动进入该清单。另一方面，受保护路径的原子写可能生成 `.file-guard` 备份；因此涉及简历摘要时必须先设计备份范围、读取权限和删除语义，不能声称删除主文件即彻底删除。现有会话日常备份与侧车是否纳入、数据最小化策略须明确决策。
5. **并发 / 崩溃**：本阶段顺序执行不自动等同单写者（UI、恢复、重试或多个进程仍可能冲突）。实现前规定谁拥有写入、并发如何排除 / 冲突如何报告、先持久化哪些标识及幂等键；如果执行已成功而记录写入失败必须呈现未存档，不能重新执行有副作用的动作。故障注入与重启验证在临时目录进行。
6. **权限**：工具读取另一会话的 `read_file` / `grep` 有确认判断。新接口不能通过内部 sidecar / 搜索索引绕开相同边界；第一阶段限制当前会话，且项目 / 独立文件引用也须经现有路径和权限校验。跨会话搜索的产品意图不等于用户授予所有历史自动访问权限。
## 1. 范围与不做

**本阶段：**同一会话内顺序执行；目标可为已绑定项目或无需绑定的独立事项；有明确要求才跟踪，拿不准时不单独建记录；要求变更、结果和证据可追溯；用户询问时可在当前会话的授权边界内查回。

**不做：**多项目可写 worker / 并发、自动判断后直接多目标写入、卡片 UI、30 秒 / 30 分钟计时、跨会话自动检索、按天目录和久远记忆自动升格、模型训练、恢复旧 TASKS / runaway、修改现有默认重试 / 修复预算或另建 Goal 预算。历史对象通过当前会话引用时仍不得突破现有项目 / 主机 / 外部路径权限。

## 2. 候选数据契约（逻辑示例，不是已定磁盘 schema）

- `conversation_id`：关联现有会话，不表示项目身份。
- `work_item_id`：系统生成且不可由标题推断；`scope` 为 `project` 或 `independent`；项目使用稳定 project_id，独立事项引用授权对象，不强制创建项目。
- `requirement_id`：标识每项要求，与原请求建立可验证来源。找不到可靠消息 ID 时先显示来源不可用，不回填猜测 ID 或引用 UI 行号。
- `execution_id` / `result_id`：同一事项续作有不同工作过程；结果包含状态、已做 / 未完成、实际验证与证据引用。缺失是 `unknown` / 未记录，不等于通过。
- `source_refs`：对现有消息、回执或文件的受控引用；保留来源类型及可访问性，不复制整份简历或秘密，不把当前文件内容推断为历史事实。
- 结果、修改记录与用户查看 / 验收不是同一状态；已完成单项不代表整个事项完成。
- 遇到对象不明确、多份简历或项目归属冲突，先问用户，不自动合并。

### 候选持久化选项

优先研究复用现有持久化与 `file_guard.atomic_write_text` 保护方式；如果无法提供稳定记录，可考虑**每会话独立、版本化的结构化侧车**。是否采用侧车、存储格式与上限、敏感信息处理、备份及锁机制须在实现前依据已有路径与权限核查后定案。不要把全局日志、消息序号、overlay 或 `goal-state.json` 直接当作完整工作记录。

对外表现约束：工作已经发生但记录失败时，分别报告执行结果与存储失败，不能重复执行修改来“补记录”；结果不确定则不声称完成。新旧会话兼容，缺失记录不意味着历史从未发生。若使用侧车，第一阶段不得假设跨文件原子事务：定义可恢复的写入顺序和异常中间状态，并保持重复回执幂等。

### 2.1 推荐方案：会话侧车快照（候选，不是实施授权）

**推荐范围：**第一阶段只在当前 `Session.session_dir` 内为明确需要跟踪的事项维护一个独立、版本化 JSON 快照，候选文件名 `work-records.v1.json`；不改 `messages.jsonl` 格式，不跨会话搜索、不把模型摘要冒充回执，也不承诺旧消息稳定引用。此选择尚须完成权限、敏感信息和备份方案审核；涉及用户数据前不得直接创建。

**形状示例（虚构测试数据，非最终 API）：**

```json
{
  "schema_version": 1,
  "conversation_id": "example-session",
  "revision": 3,
  "items": [
    {
      "item_id": "item-a",
      "scope": {"kind": "project", "project_id": "project-a"},
      "title": "登录页面",
      "requirements": [{"requirement_id": "req-a", "text": "调整页面", "status": "completed"}],
      "runs": [{
        "run_id": "run-a",
        "requirement_id": "req-a",
        "status": "completed",
        "result_summary": "页面已调整",
        "verification": {"status": "not_recorded", "summary": ""},
        "sources": [{"kind": "legacy_message", "reference_status": "unavailable"}]
      }]
    },
    {
      "item_id": "item-b",
      "scope": {"kind": "independent", "object_ref": null},
      "title": "修改简历",
      "requirements": [{"requirement_id": "req-b", "text": "精简介绍", "status": "pending"}],
      "runs": []
    }
  ]
}
```

- 身份使用系统生成、不可重用的随机标识；示例值仅为可读展示。`conversation_id` 校验必须与实际已授权会话相符，不能用请求提供的任意路径或 ID 拼接目录。`project_id` 验证现有绑定 / 实际权限，`object_ref` 为受控引用且默认不含简历正文；空引用不授予写权限。
- 当前阶段采用快照 + 修订号作为**候选**；结果是否需要追加事件日志、如何保留纠错前历史必须在最终规格确定，不能仅靠快照覆盖历史。来源字段允许不存在或不可访问，字段不能填“猜出的消息 ID”。记录摘要只表达有依据的事实，完整证据留在受控原来源。
- 对话与侧车分属不同文件：不得声称同时原子提交。记录引用对话时必须确认来源已保存且可定位，否则写入 `unavailable`，回答时明确说明；若先收到执行结果、后写侧车失败，只能显示未存档 / 状态待确认，不能隐瞒或重复执行。

### 2.2 写入所有权、故障与恢复契约（候选）

1. **写入所有权**：只允许受控的当前会话记录服务更新快照，所有上层操作走同一入口；写入前验证 session、scope、大小和 schema。进程内必须序列化读改写；跨进程必须使用经核对的会话级互斥方案或拒绝第二写入者，不能只靠 `threading.Lock` / `atomic_write_text`。仓库 `managed_store.py` 有跨平台文件锁相关实现，但属于另一条 managed 路径，能否安全复用及路径 / ACL / 异常行为必须单独核验，不能直接把它视为现成通用锁。
2. **防丢更新**：每次读到 `revision` 后，在同一互斥保护中核验当前版本、写新版本；版本冲突则返回冲突，不盲目覆盖。只有单文件写入成功后才返回“记录已保存”。不可将结果写入失败当成实际操作失败，更不可自动再次执行写入、发送、发布或有费用操作。
3. **幂等**：写入 API 接收稳定的操作 / 结果 ID；同一 ID 重复提交相同内容返回原结果，不重复追加；同 ID 不同内容报冲突，不静默覆盖。ID 如何从真实回执获取仍须核验；不能把工具调用 ID 当成所有结果的天然稳定 ID。
4. **故障处理**：侧车缺失与空会话可正常建立；格式损坏 / 未知版本 / 会话 ID 不匹配时只读阻断并提示，不能当空记录覆盖。磁盘异常、锁获取失败、版本冲突应保留已有文件并向用户说明。任何临时文件、备份及删除策略需遵守 `file_guard` 和用户确认边界；不得自动清理用户数据。
5. **重启**：只恢复最后可靠保存的记录和版本，不自动恢复执行。运行中记录恢复为待核实的候选状态，需检查实际情况；此状态与现有 Goal 恢复逻辑保持一致但不直接修改 Goal。未落盘记录无法承诺恢复。
6. **隐私 / 备份前决**：现有会话滚动备份不自动包含侧车；原子保护可能产生单文件备份。必须在创建真实记录前确定侧车是否备份、文件权限、摘要脱敏、保留及删除范围；在此之前不得宣称“已实现默认永久保留”或“彻底删除”。

### 2.2A 锁、版本历史与备份：进一步核对结果及推荐边界

**锁现状：** `managed_store.py` 中的 `_ProcessLock` 使用 Windows `msvcrt.locking` / 非 Windows `fcntl.flock`，是私有实现，并依赖 managed store 自己的受控根目录、绑定与锁文件校验；不能把私有类直接当作当前 Session 的通用锁。普通 server 的 `_repl_lock` 是进程内锁，无法证明多进程互斥。

**推荐锁契约（仍待实现前审核）：**

- 当前会话唯一的受控记录入口对每次读改写先取得进程内互斥及对应会话的跨进程锁，再读取 revision、校验、原子替换并释放；只读方只读取可解析的已发布版本。锁路径从已验证 `Session.session_dir` 派生，不接收任意用户路径；必须防越界 / 链接替换，并复核 Windows 的 junction / reparse-point 行为。
- 锁忙、校验不通过或超时应立即给出可观察的“记录暂不可写”，不等待无限期、不删除锁文件强行抢占、不继续修改其他记录。进程异常结束时依靠经实测的 OS 锁释放，而不是依据时间删除锁；文件系统 / 环境不支持所需锁语义时禁用写入并告知，不宣称安全。
- 原子替换只保护单次文件发布，不保证多个文件事务或断电后持久；真实持久性保证和 flush / sync 要在支持平台验证。持锁必须覆盖 revision 比较与替换，防止检查之后被其他进程更新。

**版本历史候选：** `work-records.v1.json` 内保留事项当前投影及有稳定 event_id 的最小历史变更（创建、要求修正、结果、受阻 / 停止），每次在锁内发布新快照；历史事件不可被后续修正覆盖。去重依据稳定 event_id + 内容摘要；相同 ID 同内容视为同一次提交，不同内容报冲突。此处的 event_id 是候选新记录身份，不是对旧消息自动补造 ID。

- 此方式避免并行维护第二套日志，但快照会随历史增长；第一阶段必须给文件大小和内存设置**可验证的安全限制**，遇限停止新增并提示，不裁剪、不悄悄删除。具体数值和未来分页 / 增量存储，在测量后单独确定；不得假称可无限保存或适用于 999 件事项的生产负载。
- 修正只追加新的变更；用户要求删除时仍按已约定的范围与确认执行。摘要和路径可能含敏感信息，不记录整份简历正文、原始密钥、完整工具日志；需要设计日志 / 错误消息脱敏，不能依靠隐藏卡片保护隐私。

**备份现状与推荐：** `backup_session_files` 只复制固定的三个文件，且 `guard_snapshots.py` 的 `SESSION_FILES` 也固定限定它们。将侧车纳入现有快照绝不是只改复制列表；还须同时审查快照清理识别、已有备份、权限和数据删除。`atomic_write_text` 的 `.file-guard` 备份是另一条路径。第一阶段不自行扩大备份清理或批量删除范围；在真实用户数据写入前，必须明确侧车及其备份的保护、保留与确认删除语义。

**重要测试安全修正：** 现有 `agent-core/tests/test_cross_session_read.py::test_read_file_other_session_requires_confirm` 使用 `AgentPaths.discover()` 和固定测试会话名，并在 finally 删除测试会话目录；不能未经隔离就将它当作绝对无副作用的验收。实施时优先用全新临时 agent root 及随机 ID 建立等价聚焦测试，运行前核对目标路径；不运行任何指向真实用户会话的清理。
### 2.3 最小定向验证矩阵（计划，未运行）

| 场景 | 输入 / 操作 | 必须观察到的结果 |
|------|-------------|------------------|
| 兼容 | 无侧车的旧会话，含无 ID 的历史消息 | 正常载入，不改旧消息、不造 ID；来源不可用清晰表达 |
| 归属 | 同会话一个项目事项 + 一个独立简历事项 | 身份不同；独立事项不改变会话项目绑定；两者证据不混 |
| 部分完成 | 项目两项要求，第一项有实际结果，第二项仍进行 | 单项结果持久化，整体不误标完成 |
| 幂等与冲突 | 同一结果 ID 同内容重送，再以不同内容重送 | 前者不重复，后者冲突并保留原有数据 |
| 并发 | 两个独立进程对同一会话尝试写入不同 revision | 互斥或明确拒绝 / 冲突，无静默丢更新；在受支持 Windows 环境验证 |
| 异常 | 模拟写入失败、损坏、未知版本和关闭前中断 | 旧内容不被空覆盖；有副作用操作不自动重做；状态及记录失败如实报告 |
| 权限 | 尝试引用其他会话 / 越界文件 | 不因新记录服务绕过现有确认或路径权限；引用缺失不泄露内容 |
| 检索 | 过几轮对话后查项目与简历的记录，证据缺失再查 | 清楚区分对象、范围与验证；没有证据不编造；模型以测试替身模拟 |
| 隐私 | 简历摘要及目标引用、删除请求与备份路径 | 不默认复制正文；不自动删除原文或假称备份清除 |

此矩阵不验证真实 LLM 理解、真实多项目并发、卡片界面、跨会话历史或生产安全；这些必须单独获授权并验收。
