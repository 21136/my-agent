# BUG-030：狂奔把文档待补齐误判为用户阻塞

## 现象

狂奔执行项目初始化时，文档尚未满足设计确认标准，系统直接显示“文档尚未达到设计确认标准”并要求用户处理后重新开启狂奔。但用户既没有缺失项清单的编辑入口，也不应该被要求理解内部文档闸门。

## 根因

狂奔检查点推进在 `documentation` 阶段直接调用 `confirm_project_design()`。当 `PROJECT.md`、`DESIGN.md`、`TASKS.md` 或 `VERIFY.md` 缺少必要内容时，异常被当作真实阻塞写入 `paused`，没有把缺失项交给当前项目内的 Harness 继续补齐。

## 修复契约

- 文档不完整是可修复的阶段状态，不得直接暂停并要求用户处理。
- Harness 应在当前项目范围内生成或修正文档，重新检查设计确认标准，再进入 design/implementation。
- 只有权限、路径越界、用户明确停止、重复失败或预算耗尽等真实安全边界才进入 `paused`。
- 用户界面可以展示“正在自动补齐文档”，不能把 `documentation` 闸门伪装成用户决策。

## 修复状态

已修复：文档标准未满足时会自动续接当前项目内的文档修复；已有暂停状态可从详情中一键恢复，不需要用户手动猜测或确认普通计划。恢复动作复用已有狂奔设置消息并携带恢复标记，避免前后端未同时重启时出现未知消息类型。

## 验收

- 狂奔在 `documentation` 阶段发现缺失内容时，自动发起一次文档修复续接，不弹人工确认。
- 文档修复成功后自动确认设计并进入下一阶段。
- 文档修复无法完成时，详情明确说明具体失败原因和可执行的人工处理方式。
