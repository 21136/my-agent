## 当前实现与验收状态（2026-11-09）

### 已有实现（以源码为准）

- 主 Agent 通过 `run_project_workers` 派发显式列出的项目任务；工具参数要求项目 ID、任务和读写路径，不从侧栏当前项目推断派工目标（`agent-core/agent.py`）。
- `ProjectWorkerHost` 接受登记的内部项目，以及经过 `external_project` 显式接入、绑定校验通过的外部项目；worker 使用绑定的规范根路径而非任意前端路径，并对项目根和目标做身份/范围校验（`agent-core/project_worker_host.py`、`project_worker_execution.py`、`project_worker_model_loop.py`）。接入目录不自动授权；只支持 registry 中绑定有效的目录，不等于任意路径沙箱或任意命令隔离。绑定/根身份在确认后变化时 fail closed。
- 批次支持最多 25 个任务排队，同一项目不重叠执行，最多两个 worker 同时运行；同一项目的后续任务等待空位（`project_worker_host.py`）。
- 有批次范围授权、精确模型外发确认、文件写入确认、取消与身份校验；运行结果和验证状态分开记录。worker 返回不等于验收通过，派工结果的 `acceptance_status` 初始为 `not_run`。
- 桌面端有确认预览和按会话/运行绑定的短时 worker 进度快照；“当前工作”概况现可对当前 Session 的非运行事项写入队列/等待确认/停止/继续准备控制、依赖元数据、优先级，并展示有限历史尝试。运行中的事项不由概况按钮假称停止，需走执行 host 的 Stop。
- 当前工作可显式选择最多六个已映射项目，主机显示项目→来源 Session 并逐项取得只读授权后，才聚合这些项目 Session 内对应 project scope 的结构化记录；拒绝授权不会读取来源记录。选中来源带 Session/revision provenance，映射或源版本在读取过程中变化则整体拒绝。当前 Session 的 independent/项目记录与所选项目来源分别投影；跨 Session 已读回执未知，不据此隐藏结果。结果每项目最多显示五个事项、每事项最多六条要求，最近十次尝试可展开；剩余数量明确提示，未实现跨来源聚合分页/全历史。
- 队列/依赖目前是持久化状态控制；**不会**在应用重开时自动调度。用户在「当前工作」填写范围并确认后，可通过 `work-records.schedule.dispatch` 在活跃父回合内直接调用 `run_project_workers` host 路径（尊重并发上限、来源授权与逐项确认），无需模型先决是否发工具。`continue` / `queue` 控制仍只更新元数据，不会隐式启动 worker。远端来源不会被 overview query 修改；远端事项控制须逐项授权与 CAS；**远端运行中** worker 可通过主会话 host 的真实取消路径协调停止（精确确认 + 来源 revision 复核），不假装元数据已停止。
- 工作记录当前支持排队/等待确认/依赖、CAS 停止/继续准备和 0–5 优先级变更，并写入追加历史。`session.open` / 主 WS 连接时会对**非本进程 owner** 的 in-progress 要求调用 `mark_interrupted_runs_unknown`（保留 schedule claim），并在仍无法核对时发出警告；不自动继续或重派。跨来源历史：`history_scope=selected_projects_history` 分页已可由桌面「所选项目统一历史」逐页加载（来源 revision 绑定游标）。
- 当前工作详情可展示已加载要求、最近十次历史尝试并编辑其依赖；更多未加载要求需先分页载入。概况操作提供队列/等待确认/停止未启动项/继续准备和优先级；不提供对运行中 worker 的假停止，也尚未自动执行调度。
- Desktop 可选择最多六个已映射项目并请求结构化概况；用户逐项授权后才读取来源侧车。远端组显示来源 Session/记录版本，并可直接展开要求、最近历史和跳转到来源会话。远端未运行事项的记录元数据操作会触发额外精确确认和 source revision CAS；不可在概况中假称取消运行中的 worker。跨 Session 结果查看回执未知，不能据此隐藏结果。选择来源、事项操作与迟到 WebSocket 响应均绑定 request/session 身份。

## 0. 一句话

**UI 仍是一个主会话、一个主 Agent**；需要动多个项目时，主 Agent **按项目 spawn 作用域子 Agent（worker）**，每个 worker **钉死一个 project_root**，结果经现有 **overlay 回灌**；项目身份继续走 ind_project_dir / workspace junction，**不新建项目库，不重建 LangGraph / TASKS / runaway**。

## 3. 流程示例：「同时改两个项目」

用户（同一聊天窗）：「A 项目把登录按钮改蓝，B 项目修一下 README 坏链。」

`	ext
1. 主 Agent 解析为多项目动手意图
   - 若当前是只聊：意图工具建议切动手 → 主对话中确认（见 DAY-JOURNAL §7）
2. 解析/绑定项目
   - 已在 workspace 的用 project_id
   - 缺的用 bind_project_dir（主 Agent 调；可 dry_run → 确认）
   - UI 当前项目可停在其中一个或保持原样；**不要求**来回 switch 才能开第二个 worker
3. Spawn
   - worker_A(task=改登录按钮色, project_root=A)
   - worker_B(task=修 README 坏链, project_root=B)
   - 不同 project_id 可有限并行（并发上限待定）；同 project_id 默认串行（守 T1）
4. 执行隔离
   - 每个 worker：Session 切片 active_shell=project，project_root 钉死
   - Executor 沿用 foreign_project_write / project_mode 校验
5. 回灌
   - 各 worker → format_subagent_overlay(kind=project_worker)
   - 主 Agent 合并 overlay，用一两段话回复用户；需要确认的发布/外发仍走主链，在对话中说明并确认
6. Goal（若动手已建 Goal）
   - 父 Goal.workspace_scope 可记「多项目」或列表；验收可按项目分别跑，结果写回父 Goal / notice
7. 事后记忆（未实现的日记草案）
   - 当天目录：动过项目名 = [A, B]
   - 各项目按天库：各自完整片段；日记详情只留短提示 + 链接
`

## 5. 会话 / UI 约束（防串台）

1. **主会话**继续最多一个「UI 当前项目」（project_id / 侧栏）。
2. Worker **不得**写主会话的 project_id；钉扎只在 worker 私有执行上下文。
3. 迟到的 project.state 仍按 PROJECT-SWITCH-STATE-ISOLATION 丢弃。
4. 用户问「现在在改哪个」：主 Agent 应能列出 **活跃 worker 及其 project_id**（产品可见性，实现时可先 notice）。
5. Stop：停主回合应取消未完成 worker（复用 cancel_event 模式）。

## 6. Goal Runtime 衔接

- 保持 P0：**不**跨进程自动复活 Run；Stop 后不自动续。
- 多项目长任务：优先 **一个父 Goal** + 子步骤文案点名项目；或「一项目一子预算」记在 overlay，而不是新调度器。
- 当前 Goal Runtime 对多项目批次可记录涉及的项目并将其标记为未验证；这不代表多项目验收已通过，也不代表跨进程恢复。workspace_scope 的旧 schema 建议仅为历史讨论，不是当前接口契约。

## 7. 隔离与防污染（一个会话、多项目）

> 用户关心：界面仍是一个会话，怎么同时谈/改多个项目却不串台、不陷入幻觉；若已污染怎么收。

### 7.1 隔离边界（部分由当前实现落实；产品级污染处置未验收）

1. **一个 UI 会话**：用户只面对主 Agent；不因多项目新开主会话窗。
2. **每个 project_worker 钉死** project_id + project_root；执行期内不得改绑、不得写主会话的当前项目字段。
3. **写盘只允许落在本 worker 绑定 root 下**（沿用 / 加强现有 foreign_project_write 等校验）。
4. **主 Agent 只消费带项目标签的 overlay**（project_id / worker_id）；未打标的摘要不得当作「已在某项目完成」的证据。
5. **跨项目断言必须引用来源**：说明来自哪个 worker 回执或哪条已读路径；禁止把 A 的结论安到 B 上。

### 7.2 污染判定与处置

出现串台迹象时（例如 worker 回执写了别的 root、主述把 A/B 事实混成一条、overlay 缺 project_id）：

1. **立刻停止**相关 / 全部活跃 worker（复用 cancel_event）。
2. **隔离受污染 overlay**：不得注入后续模型上下文或升格为可信记忆；保留必要的原始回执和污染标记以供排查，不静默删除证据或覆盖实际改动。
3. 向用户说明受影响范围、实际修改和不确定性；不自动回滚、重派或重跑。需要旧活线归档 / 新开线时遵守 PROJECT-THREADS 的用户显式决策与权限边界，后续处理由用户决定。
4. 经用户明确同意后，核对项目身份、范围和现状，再决定只读排查或重新派工；不把受污染结果当成功证据。

### 7.3 记忆侧打标

- 按天日记「动过哪些项目」只记 **项目名/id**；项目详情链接进「项目→按天」库（见 [DAY-JOURNAL-MEMORY](./DAY-JOURNAL-MEMORY.md)）。
- 久远记忆若沉淀与项目相关的硬事实，**必须带项目标签**；无标签不得当跨项目通则。

## 8. 主 Agent 防幻觉

主 Agent 是唯一对用户说话的编排者。下列是产品级行为要求，不应仅凭 worker 返回推定已达成；当前代码有范围绑定、授权和回执校验，跨项目叙述与污染处置仍需端到端验证：

1. **只编排 + 汇总，不自己改多个项目**：多项目写码交给对应 project_worker；主 Agent 不在同一回合里对两个 root 直接动刀。
2. **每条事实性声明**须带 **项目标签**，且能指向 **worker 回执**（或明确的工具/文件证据）；无回执不说「已改好」。
3. **吃不准就问，或再派工**：缺项目身份、缺验收、回执矛盾 → 向用户确认，或按项目重新 dispatch；禁止脑补补全。
4. **紧预算 / 紧白名单**：主侧多项目回合限制并行 worker 数与 overlay 体积；主 Agent 工具面不因「方便」扩成可写任意 root。
5. 与 §7 联动：一旦怀疑污染，走暂停→隔离不可信 overlay→告知用户并依其决定处理，而不是在混杂上下文里「再编圆一点」。

## 9. 分角色系统提示词

Worker 目前使用独立的受限系统提示词（见 `project_worker_model_loop.py`）；主 Agent 的编排与结果汇总仍由主 Agent 提示及工具链承担。以下是职责边界要求，提示词存在不等于结果正确性已验收：

| 角色 | 提示词重心 |
|------|------------|
| **主 Agent（parent）** | 编排、意图拆分、派工、汇总、防串台；禁止冒充已完成的多项目改动；强调标签与回执 |
| **project_worker** | 只服务钉死的 project_id/project_root；任务边界、可写范围、回执格式（结论 / 已改 / 未完成 / 路径） |
| explore / checker / review 等 | 保持现行只读 / 验收角色提示；不与 worker 混用同一套「可写项目」提示 |

约束：

- **人设可共享**（如小魔王语气）作为薄层前缀。
- **角色职责不得共用一个大 blob**：parent 与 worker 必须是分开的提示模块，避免「编排者」和「施工者」指令互相污染。
- Worker 提示词须显式写入绑定 root；Parent 提示词须显式禁止无回执的跨项目断言。

## 10A. 单对话、当前工作与历史（2026-10-29 确认的产品方向）

> **草案 / 未实现。** 一个人面对同一主对话与主 Agent；不要求项目侧栏、独立项目后台或新主会话。以下交互、工作记录与多项目 worker 均不能据文档推断已落地或验收。

### 10A.1 对象与作用域

- 一次请求可包含五个项目、每个项目多项要求，也可同时有修改简历等独立事项。项目是可选归属，不强制为简历创建 / 绑定项目。独立事项走适用的目标路径、意图与权限，不因与项目共屏获得 worker 权限。
- 主 Agent 区分项目、事项和证据；项目 worker 钉死作用域并遵守 §7–§9。对象不清或同名候选时先问；续作关联已有对象与记录、形成新的工作过程，不覆盖过去。修改前检查当前状态及权限。
- 跨事项引用要核实来源与权限：例如写简历前先确认项目实际成果和验证范围，以及目标简历；项目授权不等于简历写入授权，不能把计划或未验证成果写成事实。

### 10A.1b 小魔王空间 UI 表面（已编码规则）

伴侣主界面 **该显 / 该藏**（composer 独占普通确认、进度进当前工作而非聊天刷屏等）以 [WORKBENCH-UI](./WORKBENCH-UI.md) §小魔王空间为准；与本文件 §7–§9 编排/防串台要求同时生效。

### 10A.2 单对话交互

- **轻量当前工作入口**：有进行中的事、需要确认的事或尚未看过的重要结果时出现，均无时隐藏；不永久占屏。点开先看各项目 / 独立事项的整体概况、简短进展和真实状态，再点事项展开各要求；也可直接问 Agent。排队 / 受阻如何影响入口显示与异常恢复待细化，不能静默掩盖需要关注的事项。
- **对话确认**：需要确认时 Agent 直接在对话说明对象、拟做操作与影响并询问，不要求用户进入确认中心；多项问题区分归属，避免轰炸。在适用权限内普通读取、解释和整理通常直接处理；明确目标的小范围修改按现有权限执行，不为每次保存追问。删除、覆盖重要文件、大范围修改、外发或发布须事前说明影响并获确认；目标含糊先问。现行权限及风险策略仍然适用。
- **进度**：普通内部步骤不刷屏；完成、受阻或需确认等重要变化主动说明。长时间无明显变化不反复发相同消息，用户可随时问；全部事项结束后简洁汇总完成、未完成及实际验证范围。不能因静默推断仍运行或成功。
- **结果与卡片**：重要更新重发对应项目的完整工作卡片，不重发整批；同项目短时间连续普通重要更新可合并，需要立即确认或严重受阻直接说明。旧卡片保留时间及当时状态，新卡片呈现最新已知情况；当前概况只看最新状态。看过和 30 分钟收起、历史检索与证据边界以 [日记 §4.3–4.5](./DAY-JOURNAL-MEMORY.md#43-工作记录什么值得记记些什么) 为准。展示的变化必须来自真实回执，且不删除历史。

### 10A.3 工作生命周期与执行

- 明确需要跟踪的工作先形成轻量当前事项，完成、受阻或被叫停时记录实际结果与证据。拿不准是否值得单独记录时先不建记录，待用户要求再从可访问对话整理；不存在的证据不得编造。状态至少区分排队、进行、等待确认、受阻、完成、取消；失败和部分完成不得伪装为完成。schema 待定。
- 不同项目可有限并行，同一项目内的修改默认排队；区分排队与运行，不承诺所有项目同时执行。某操作等确认时暂停该操作；其他不依赖它且有权限的事项可按资源和实际能力继续，依赖项等待。具体并发、依赖及独立事项策略待设计。
- 用户指定停止某事项则按该范围处理；“都停”停止所有进行中事项并阻止排队启动；只说“停一下”而范围不明时先暂停新事项启动并询问。按实际可中断能力报告，不能假称已停止。
- 用户指定“继续 B”或“刚才停的都继续”时按范围准备继续；只说“继续”且多个事项停着时先问范围。继续前核对当前状态、权限及未解决问题。
- 关闭应用后保留已持久化的事项和进展；重新打开默认不自动执行 / 修改，简短提示未完成事项，明确要求继续后再核对。关闭时结果不明的操作标为待确认并检查，不猜测；不承诺未落盘进度可恢复。Goal P0 仍不跨进程自动复活 Run。

**用户确认的状态呈现（2026-10-29）：** 概况区分排队中、进行中、等你确认、受阻、已完成、已停止；详情区分用户主动停止与应用中断。应用关闭时操作结果不明，显示“状态待确认”，不能断言已安全停止。已完成不代表验证通过；“修复并测试”等要求若测试未完成，应如实显示未完成 / 受阻及原因。以上是产品展示方向，底层状态机、恢复和验证仍待设计。
**用户确认的项目概况（2026-10-29）：** 项目有多项要求时，概况优先突出需要用户关注的状态（如等确认或受阻），并补充其他要求的真实进展；不能因为一项完成而把全部标为完成，也不能把局部等待说成整个项目均已停下。进行中、排队、已停止与结果不明的混合场景须准确呈现；具体优先级、计数和异常状态合并规则待设计。
**用户确认的要求拆分（2026-10-29）：** Agent 可将同一请求拆成项目内要求及独立事项以便跟踪，同时保留原始请求与对应关系；“修复并测试”默认作为一个要求，测试是完成条件，不能只修复就判整项完成。归属或目标不清先问；仅拆分方式略有不确定且不影响权限和执行时可先合理处理。用户可要求合并或拆分展示及关联，不删除既有记录；具体身份、版本、映射及实现待设计。
**用户确认进行中要求变更（2026-10-29）：** 用户变更正在处理的要求时，先识别其指向；能可靠确定则更新原事项的要求并保留变更及已产生的实际结果，不覆盖历史。尚未执行到的步骤按新要求处理；已做出的改动可按新要求继续调整，但仍需满足现有权限和风险边界。指向不清或高风险时先问；操作无法立即安全中断时如实告知，不假称变更已生效。用户明确停止某项时不影响无依赖的其他事项；版本、并发冲突、持久化与执行细节待设计。
**用户确认误解及串台纠正（2026-10-29）：** 用户纠正事项归属或理解时，未执行则修正展示和归属；已执行但未修改则停止错误方向、修正后按适用权限继续；已产生修改则如实说明实际影响，再由用户决定后续处理，不自动回滚或删除。已有记录保留原始请求及实际发生的事实，追加修正并以后使用已修正的关系；疑似跨项目 / 文件污染时暂停相关工作，核查范围，不静默掩盖。具体中断、纠错审计和污染恢复待设计。
**用户确认默认项目并行上限（2026-10-29）：** 默认最多两个不同项目同时执行修改；其余排队，同一项目内修改默认排队。项目结束或进入等待后，按依赖、授权、资源及实际执行状态决定是否安排其他项目；等待并不必然意味着执行体已释放，不能突破上限。具体并发计数、可配置范围、独立事项具体资源策略及首阶段串行验证待设计；目前未实现或验收。
**用户确认独立事项并行原则（2026-10-29）：** 独立事项不占项目修改名额，但第一版默认最多一项独立文件修改并行；默认上限方向为两个不同项目修改 + 一项独立文件修改，实际仍受权限、依赖、资源及隔离约束。同一文件不得并发写，包括项目与独立事项之间，须排队；只读回答不机械占写入名额，仍遵守权限与资源限制。路径别名 / junction / 符号链接、冲突检测、锁释放与异常恢复须在实现前设计验证，不能仅凭显示名称判断；这些能力未实现或验收。
**用户确认排队与优先级（2026-10-29）：** 用户明确指定优先级则按其意图处理；未指定时默认按提出顺序安排，依赖未满足的事项等待。需确认或受阻的事项不阻塞互不依赖且获授权的后续工作，但仍受并行上限、写冲突与资源约束；用户可调整尚未开始事项的顺序，已执行操作是否可中断须如实说明。这里是轻量工作编排的产品方向，不恢复已退役的 TASKS / runaway 调度机制；具体排序、持久化及异常恢复待设计。
**用户确认当前概况数量（2026-10-29）：** 点开当前工作入口时默认最多显示 6 个项目 / 独立事项，优先展示需确认、受阻、进行中等需关注状态，再显示排队事项；超出时明确“还有 N 项”，可展开，也可通过对话询问。显示排序不改变实际执行或排队顺序；未查看的重要结果、停止 / 状态待确认等混合排序与可访问性待设计，不得静默隐藏需要关注的问题。
**用户确认暂时离开时的处理（2026-10-29）：** 应用仍运行、用户仅切换窗口或暂时离开时，已授权且实际仍可运行的工作可继续；需确认的操作等待用户，不依赖确认且有权限的事项可继续，不因未回复自动代答、取消或扩大范围。用户回来可在对话询问，由 Agent 根据实际状态与记录汇总；关闭应用仍不自动续跑。锁屏、休眠、系统资源中断等实际运行能力及异常恢复待设计和验证。
**用户确认有限重试（2026-10-29）：** 故障处理允许有限重试，不无限静默重试；只读操作的临时故障可自动有限重试。结果不明确且重复执行可能产生副作用时先核验实际结果，仍无法确定则询问用户，不直接重试；不能据此视为自动重复写入 / 外发的授权。核验方式与各类副作用权限仍待设计；只读临时故障次数及测试失败处理见下。
**用户确定只读临时故障重试目标（2026-10-29）：** 对未来明确划定的只读临时故障策略，目标为默认最多额外重试 5 次，即包含首次尝试最多 6 次；仍失败则停止并告知用户。明确不可由重试解决的权限不足、文件不存在等不盲目重试；用户停止时不再发起后续重试。间隔 / 退避、临时故障判定、预算及取消边界待设计；有副作用且结果不明时仍先核验、无法确定则询问，不按此自动重试。
**用户确认测试失败处理（2026-10-29）：** 保留和报告真实失败结果；在原授权范围内分析并可尝试修复，修复后运行相关测试验证，不无限循环。原因不清、修复扩大范围或连续尝试仍失败时停止并说明、询问用户；不得删除测试掩盖失败。修复循环与只读临时故障重试分别计算，默认轮数见下；测试风险 / 权限及细化停止条件待设计。
**用户确认测试修复目标（2026-10-29）：** 产品目标为默认最多 3 轮自动修复；一轮为分析失败、一次针对性修复及相关测试验证，保留真实修改与结果。原因不清、需要扩大授权范围或有风险时提前停止并询问；3 轮仍失败则停止并汇报已做内容与当前状态。不删除测试或修改断言掩盖失败；与只读临时故障重试分开计数。持久化计数、预算、重启与并行隔离机制待设计。
**用户确认重试过程可见性（2026-10-29）：** 各次尝试及结果保留于工作记录或可追溯执行详情，不逐次刷对话；当前工作可显示简洁的实际进度与轮数。成功后在结果卡片或汇总说明；达到上限、需扩大范围或需确认时及时对话说明。用户可询问尝试过程，由 Agent 在权限内检索；详情保存失败 / 缺失时如实报告，具体持久化与隐私待设计。
**与现有机制兼容核对（源码只读观察，2026-10-29）：** `goal_runtime.py` 现有默认 repair_limit 为 3，但 repair_count 由验收失败驱动，不等同于上面的“分析→修复→测试”轮次；不要新增平行计数或改变语义，须先确定复用 / 映射及用户认可。`agent.py` 和 `exec_reliability.py` 现有模型传输、空回复及工具参数纠错等各有上限 / 终止规则；只读故障“额外 5 次”是新策略目标，不覆盖现有重试，更不自动增加模型调用。桌面确认链已有单个当前 confirmOverlay、处理旧确认的逻辑；并行多事项的请求身份、排队及取消要先设计，不能假设并发确认已支持。上述观察不是运行验收。
