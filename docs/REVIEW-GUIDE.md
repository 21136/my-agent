# my-agent 评审指南

供多个 LLM 或人工评审者使用。请先完整阅读 [PROJECT.md](./PROJECT.md)，再按本指南逐项给出意见。

---

## 评审任务

请从 **架构师 / 产品 / 安全 / 个人开发者** 视角，对 my-agent 项目文档进行评审。输出结构建议如下：

```markdown
## 总评（1～10 分 + 一句话）
## 优点（2～5 条）
## 问题与风险（按严重程度排序）
## 对开放问题的回答（可选）
## 具体修改建议（可落地的）
## MVP 范围评价（是否过大/过小）
```

---

## 评分维度

| 维度 | 考察点 | 权重 |
|------|--------|------|
| **问题定义** | 是否准确抓住通用 Agent 边界与个人进化价值？ | 15% |
| **架构清晰度** | 三层分离、进化层与内核边界是否清楚？ | 20% |
| **进化协议** | 提议→确认→落盘→回滚是否完备？会否进化歪？ | 20% |
| **可行性** | MVP 能否在 1 人 + U 盘条件下实现？ | 15% |
| **安全与可逆** | 个人场景下风险是否可控？ | 10% |
| **场景贴合** | Word 模板策略是否是正确切入点？ | 10% |
| **可扩展** | 未来加 UI、向量、多 LLM 是否留足空间？ | 10% |

---

## 必答问题

1. **最大硬伤是什么？** 若只能指出 1 个可能导致项目失败的点，是什么？
2. **MVP 应砍掉什么？** 当前 MVP 是否仍过大？
3. **进化协议是否足够？** 是否需要「技能失效检测」「定期审阅」机制？
4. **技术栈建议**：Python CLI 是否是最佳起点？有无更轻或更稳的选择？
5. **与现有生态关系**：应复用 Cursor skills 格式，还是自建标准？
6. **U 盘方案隐患**：2TB 便携是否应改为「U 盘只存 evolve，代码在 git」？

---

## 可选深入问题

- 如何防止 `evolve/skills/` 膨胀导致 context 爆炸？
- 是否应为每条 memory 加 `expires_at` 或 `confidence`？
- proposal 是否应由 **第二个 LLM** 审校后再呈现给用户（避免自我强化偏见）？
- Word COM 在无 Word 环境下的降级策略？
- 是否需要 `agent-core` 的 semver，与 `evolve/` 版本解耦？

---

## 评审时需警惕的「假优点」

以下听起来对、但可能误导，请刻意挑战：

| 说法 | 挑战角度 |
|------|----------|
| 「越用越强」 | 是否实为「越用越乱」？有无 prune 策略？ |
| 「个人用所以安全」 | 进化脚本误删文件、API key 泄露是否仍可能？ |
| 「模板解决 Word」 | 用户不愿维护模板时怎么办？ |
| 「CLI 够快」 | 日常是否会因无 UI 而放弃使用？ |
| 「可插拔 LLM」 | adapter 层是否会增加 MVP 负担？ |

---

## 期望输出质量

- 避免空泛表扬或空泛批评
- 每条建议尽量指向文档章节（如「见 §4.3 进化协议」）
- 若建议新增机制，请说明 **代价** 与 **MVP 是否纳入**
- 若认为项目方向错误，请给出 **替代方向** 而非仅否定

---

## 提交评审结果的方式（给项目作者）

作者可将不同 LLM 的评审汇总后：

1. 更新 `docs/PROJECT.md` 版本号
2. 在 `docs/CHANGELOG.md` 记录采纳/拒绝项
3. 将争议点保留在开放问题直至 M1 前关闭

---

## 评审清单（快速勾选）

- [ ] 读懂三层架构与进化边界
- [ ] 评估 Word 场景策略是否现实
- [ ] 检查 MVP 范围与两周验收标准
- [ ] 检查 U 盘/portable 风险
- [ ] 回答至少 3 个必答问题
- [ ] 给出 1 条可立即执行的修改建议
