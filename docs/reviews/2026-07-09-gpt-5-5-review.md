## 总评（7/10）

**一句话总结**：项目方向抓得准，Word 模板策略和「外挂式进化」边界务实，但 MVP 仍把「先证明个人价值」和「搭建进化系统」混在一起，最容易导致先做框架、后发现日常不用。

---

## 优点（2～5 条）

1. **问题定义清楚，且没有迷信通用 Agent。** §2.1 对 Word 格式丢失、OOXML 有损抽象、Computer Use 脆弱性的判断基本准确；附录 A 也明确把 Computer Use 放在可选工具位，而不是主路径。

2. **三层架构有利于控制风险。** §4.1 将对话层、`evolve/` 进化层、`agent-core/` 内核分开，§4.2 又明确 L4 内核和 L5 模型不自动进化，这个边界对个人项目非常关键。

3. **进化协议保留了审计线索。** §4.3 要求每条记录包含 `source`、`evidence`、`content_path`，这比单纯写一条 memory 更可追责，也便于后续回滚和清理。

4. **非目标列表有工程克制。** §3.2 明确不做 SaaS、多用户、任意复杂 Word 无损自由改写、自主 fine-tune，避免了个人项目常见的范围失控。

5. **Word 场景选择正确。** §5 将目标从「任意 docx 完美复刻」收缩为「模板 + 书签/占位符替换」，这是当前条件下更接近可交付价值的方案。

## 最大硬伤（1 个）

**最大硬伤：§7 的 MVP 没有先验证最核心的日常收益，而是先建设一个通用进化框架。**

项目真正的价值假设不是「Agent 能生成 proposal」，而是「这个人每天处理 Word/文档任务时，模板链路 + 少量个人规则能显著省时间」。但 §7.1 和 §7.3 把 CLI、基础工具、proposal 流、state、evolve_log 都放在 Word 模板链路之前，§7.2 的验收指标也偏向系统内部产物数量，例如 memories 数量、skill 命中次数，而不是用户是否更快完成一份真实文档。

如果前两周做出了 CLI 和 proposal 流，却还没有跑通一份真实模板文档，项目会得到一种虚假的进展感：框架在成长，但核心痛点尚未被证明解决。这个硬伤会导致项目失败，因为个人项目最稀缺的不是架构空间，而是持续使用动机。

## 问题与风险（按严重程度排序）

### P0：MVP 验收指标测的是「系统长了什么」，不是「用户省了什么」（见 §7.2）

§7.2 当前指标包括 `memories/` 条目数量、skill 路由命中、Word 链路出现次数。这些指标能证明系统有活动痕迹，但不能证明用户净收益为正。一个系统可以满足「5 条 memory + 1 个 skill 命中」，同时让用户花更多时间审 proposal、改模板、处理误路由。

建议将第一验收指标改为用户行为结果：两周内至少完成 1 次真实 Word 模板填充任务，且相比手工流程明显减少重复操作。数量型指标可保留为辅助，不应作为 MVP 成败主判据。

### P1：进化协议只有「写入侧」，缺少「使用侧」闭环（见 §4.3、§4.4、§7.2、§10.2、§10.8）

§4.3 描述了 proposal 如何生成、确认、落盘，但没有定义落盘后的 memory/skill/tool 如何被选择、注入、命中、评估和废弃。§7.2 又要求「被实际引用」和「skill 被路由命中」，但 §4 没有给出最小路由规则。

这会让 MVP 在实现时遇到一个空洞：系统知道如何长出 skill，却不知道什么时候该用它，也不知道用错后如何降权。建议在 §4 增加「使用侧协议」：候选发现、命中理由、引用日志、用户反馈、降权/归档规则。

### P2：U 盘便携叙事低估了丢失和泄露风险（见 §3.1、§6.1、§6.2、§9 R2、§10.7）

§3.1 和 §6.1 强调整体驻留 U 盘，§9 R2 只写了 U 盘损坏导致数据丢失，但没有把 U 盘丢失后的隐私泄露列为同等级风险。项目处理的可能是合同、标书、红头文件、对话摘要和个人偏好，这些内容比代码更敏感。

建议 §9 新增风险：U 盘丢失导致 `data/conversations/`、`templates/`、`workspace/` 泄露。§6.2 应明确：代码与 `evolve/` 走 git/私有远端，敏感 workspace 和全文对话默认不提交，U 盘只是便携介质，不是唯一可信存储。

### P3：安全边界目前更像约定，不是技术约束（见 §6.4、§9 R4、附录 B）

§6.4 写到工具脚本默认在 `workspace/` 下操作，§9 R4 写通过限定 workspace 和确认执行降低破坏性操作。但 Python、PowerShell、Word COM 本身不会被这个目录约定限制；脚本一旦执行，仍可访问 U 盘外路径或本机用户目录。

建议把措辞改得更诚实：MVP 仅提供「人工确认 + 路径约定 + dry-run 优先」的软边界，不声明沙箱。真正技术沙箱、权限隔离或只读挂载应标为后续工作。

### P4：Word 模板策略正确，但缺少模板生命周期设计（见 §5.2、§5.3、§7.3）

§5.2 假设第 3～5 次能沉淀「使用 templates/xxx.docx，仅改书签」，§5.3 只说明 `templates/` 存母版，但没有说明模板如何创建、版本化、校验和淘汰。现实里模板会改版，书签会丢，甲方格式会变化。

建议新增 §5.4「模板生命周期」：模板命名版本、书签清单、填充前校验、输出对比、旧模板归档。MVP 至少要做「书签存在性校验」，否则生成成功但内容写错位置会比失败更危险。

### P5：技术栈表把后期扩展提前放进 MVP 心智（见 §6.3、§7.1）

§6.3 同时列出可插拔 LLM、JSON + SQLite、可选向量检索、Git；§7.1 又把 state 和 evolve_log 放入 MVP。虽然部分内容标了可选，但读起来容易把「未来可扩展」误当成「现在要设计完整接口」。

建议把 §6.3 拆成「MVP 固定选择」和「后续扩展」。MVP 应固定为 Python CLI + 单一 LLM adapter + 文件系统 JSON/Markdown + Git 手动备份，其他只保留接口意识，不实现。

## 对必答问题的回答（6/6）

### 1. 最大硬伤是什么？

最大硬伤是 §7 的 MVP 顺序错误：先做通用进化系统，后验证最核心的 Word/个人文档收益。这个问题比某个技术选型更致命，因为它会消耗个人项目的早期动力。建议把「真实 Word 模板链路」提前到 M0.5 或 M1 的第一交付。

### 2. MVP 应砍掉什么？当前 MVP 是否仍过大？

当前 MVP 仍偏大。建议从 MVP 砍掉：

| 建议砍掉 | 指向章节 | 理由 |
|----------|----------|------|
| 可插拔多 LLM adapter 的实际实现 | §6.3 | 单人 MVP 先绑定一个模型即可，抽象过早会增加调试面 |
| SQLite | §6.3、§7.1 | MVP 数据量很小，JSON/Markdown + 文件树足够 |
| 自动生成或安装新工具依赖 | §7.1 已列不包含，建议 §4.2 L3 也强调 | L3 工具风险高，应先只支持人工放入/审阅后的工具 |
| 自动 skill 冲突排序 | §10.2 | MVP 可用显式调用或简单优先级，先记录冲突，不自动裁决 |
| 完整对话全文归档 | §8、§10.7 | 隐私风险高，MVP 默认只存摘要和 proposal 来源 |
| Web/TUI 预研 | §6.3、§7.1 | CLI 足够验证闭环，UI 放到真实高频使用后再决定 |

建议增补到 MVP：

| 建议增补 | 指向章节 | 理由 |
|----------|----------|------|
| M0.5：独立 Word 模板填充脚本 | §5、§7.3 | 先证明核心场景，不依赖 Agent 框架 |
| 引用日志 `used_at` / `reason` | §4.3、§7.2 | 否则无法证明 memory/skill 被实际使用 |
| proposal 数量上限 | §4.3、§10.1 | 防止确认疲劳 |
| 模板书签校验 | §5.3 | 防止输出文件静默错误 |
| U 盘丢失风险和默认不落盘全文 | §6.2、§9、§10.7 | 个人场景仍有真实隐私风险 |

### 3. 进化协议是否足够？是否需要「技能失效检测」「定期审阅」机制？

§4.3 的进化协议作为「提议到落盘」的最小闭环是够的，但作为完整进化系统还不够。它缺少三件事：

1. **使用记录**：每次引用 memory/skill/tool 时记录 `used_at`、`reason`、`outcome`。
2. **失效信号**：用户可在任务结束时标记「这次用得不对」，连续失败后设为 `suspect`。
3. **定期审阅**：提供 `review evolve` 类命令，列出从未使用、最近失败、互相冲突、过久未更新的条目。

MVP 不需要自动 prune，但需要把发现问题的成本降下来。建议 §4.4 从「冲突与回滚」扩展为「冲突、失效与审阅」。

### 4. 技术栈建议：Python CLI 是否是最佳起点？有无更轻或更稳的选择？

Python CLI 是最佳起点，尤其因为 §6.1 的 Word 自动化依赖 Windows + Word COM，Python 在脚本、文件处理、COM 自动化、快速原型之间平衡最好。

更稳的取舍是：MVP 不要同时支持 OpenAI / Anthropic / Ollama。先固定一个 provider，用一个很薄的 `llm_client.py` 包起来即可。等真实任务跑通后，再决定是否需要多模型。

对于 Word 模板，建议优先做两条路径：

- Windows + Word 已安装：使用 COM 复制模板并替换书签。
- 无 Word 或调试环境：只做模板文件存在性、书签清单或占位符文本的静态校验。

### 5. 与现有生态关系：应复用 Cursor skills 格式，还是自建标准？

建议复用 Cursor `SKILL.md` 的外壳格式，但不要完全绑定其运行语义。§3.2 和 §8 已经受到 Cursor skills 启发，复用格式有三个好处：用户熟悉、可手工编辑、便于以后导入/导出。

同时建议自建一份轻量元数据，例如 `evolve/skills/<name>/meta.json`：

```json
{
  "id": "word-template-fill",
  "status": "active",
  "source": "conversation_id",
  "evidence": "原始对话摘录",
  "use_count": 3,
  "last_used_at": "2026-07-09T15:00:00+08:00",
  "failure_count": 0
}
```

也就是说：内容格式复用 Cursor，生命周期和使用数据由 my-agent 自己管理。

### 6. U 盘方案隐患：2TB 便携是否应改为「U 盘只存 evolve，代码在 git」？

建议改为：**git 是 source of truth，U 盘是便携运行介质和本地工作区，不是唯一存储。**

更具体地说：

| 内容 | 建议归属 | 理由 |
|------|----------|------|
| `agent-core/`、`docs/` | Git | 代码和文档应可恢复、可 diff、可回滚 |
| `evolve/` | 私有 Git，可加密远端 | 这是项目核心资产，不能只放 U 盘 |
| `templates/` | 私有 Git 或加密备份 | 模板敏感但也重要，至少要有备份策略 |
| `workspace/` | U 盘本地，默认 gitignore | 可能含客户/合同/标书文件 |
| `data/conversations/` | 默认只存摘要，全文可选 | 降低 U 盘丢失泄露面 |
| API key | 本机环境变量或系统密钥库 | 不应放在 U 盘明文文件 |

§6.1 的「插盘即用」可以保留为体验目标，但文档应承认换机需要安装运行时、配置 key、拉取 git 或同步 evolve。

## MVP 范围评价（是否过大/过小）

**结论：当前 MVP 过大，而且价值验证顺序应前移。**

建议将 MVP 改成三步：

| 阶段 | 建议范围 | 验证目标 |
|------|----------|----------|
| M0.5 | 独立 Word 模板填充脚本，无 LLM | 模板策略是否真能解决核心痛点 |
| M1 | Python CLI + 单 LLM + 文件读写/列目录/调用已审核脚本 | Agent 是否能稳定调度已有工具 |
| M2 | 每次 `exit` 时最多生成 1～2 条 proposal，用户确认后落盘 | 用户是否愿意参与轻量进化闭环 |

MVP 应砍掉：SQLite、多 provider、向量检索、自动 L3 工具生成、自动复杂路由、Web/TUI、全文对话归档。

MVP 应增补：模板校验、引用日志、proposal 上限、U 盘丢失风险、默认不落盘全文、最小审阅命令或审阅清单。
