## 总评（7/10）

方向正确、边界清醒，但「进化写入」写得很完整，「进化读入 / 路由 / 治理」几乎空白——两周验收会卡在这里。

---

## 优点（4 条）

1. **问题定义准**（§1、§2.1）：抓住「通用 Agent 预装能力 vs 个人真实流程」错位；Word 用模板 + 定点替换而非 Computer Use，判断扎实。
2. **非目标写得好**（§3.2）：明确不做静默进化、不改内核、不 fine-tune，把高风险挡在门外。
3. **进化分层清晰**（§4.2）：L1–L5 自动度与风险对照表；原则「进化外挂而非黑盒自改」可执行。
4. **风险表有用**（§9 R1–R6）：错误固化、膨胀、路径、破坏性脚本都点到了，且与 §4.3 / §6.4 对策能对上。

---

## 问题与风险（按严重程度）

### P0 — 最大硬伤：有「写入协议」，无「消费闭环」

§4.3 把提议 → 确认 → 落盘 → 回滚写清楚了，但 **memories / skills 如何进入上下文、如何被路由命中、命中失败怎么办** 几乎未定义；§10 开放问题 #2、#8 仍悬空，而 §7.2 验收却要求「skill 被路由命中」「模板链路被走通」。

结果：两周后 `evolve/` 可能堆满文件，agent 行为仍像第一天——核心命题「越用越贴合」无法被证伪或证实。这比「U 盘坏了」或「CLI 不好用」更致命。

### P1 — 「越用越强」缺治理，易变「越用越乱」

§9 R3 提了 prune，但无触发条件、无失效检测、无定期审阅；§4.4 冲突只说「显式提示」。没有 prune / 失效机制时，确认流只能防「写坏」，防不了「写多」。

### P1 — MVP 仍偏大（§7.1 + §7.3）

M1–M4 串了：CLI、LLM、基础工具、proposal 流、Word COM、回滚 + git。一人 + U 盘两周，COM 环境差异 alone 就够拖死 M3；可插拔 LLM（§6.3）对 MVP 是负担而非资产。

### P2 — 模板策略正确，但依赖用户维护意愿（§5.2–5.3）

策略对，文档未写「用户不愿维护模板」时的降级（只出 checklist？半自动从旧稿抽书签？）。痛点场景可能卡在「没有母版」而非「没有 tool」。

### P2 — 安全边界偏乐观（§6.4、附录 B）

「个人用所以安全」不够：`evolve/tools/` +「后期可关确认」+ U 盘随身，误删与 key 泄露仍可能。API key「U 盘外」与「插盘即用」存在张力，换机体验未写清。

### P3 — 对话层过薄（§4.1）

「聊天界面 + 基础工具」未说明 system prompt 如何组装 evolve、token 预算、skill 目录膨胀时的加载策略。

## 对开放问题的回答（6 个必答）

### 1. 最大硬伤是什么？

**进化产物缺少「读路径 + 路由 + 失效」闭环**（对照 §4.3 完整、§7.2 依赖命中、§10 #2/#8 未决）。没有稳定消费机制，确认写入只是在往文件夹堆文档。

### 2. MVP 应砍掉什么？

**仍过大。建议砍：**

| 砍 | 出处 | 理由 |
|----|------|------|
| 可插拔多 LLM adapter | §6.3 | 先钉死一个 provider；adapter 留接口注释即可 |
| Word COM 作为 M3 硬依赖 | §7.3 M3、§5.2 | 改为手写 1 个确定性脚本（复制模板 + 书签/占位符），COM 作可选增强 |
| SQLite 索引 | §6.3 | MVP 只用 `state.json` + 文件树 |
| 对话驱动自动生成 L3 tools | §4.2 L3、§7.1 | MVP 只自动提议 L1 memory + L2 skill；tool 人工放入 |
| 完整按日 backup/ 回滚 UI | §4.4、§7.3 M4 | MVP 用 git commit 当回滚；`backup/` 延后 |

**建议增补（小代价、高杠杆）：**

- **最小路由**：启动时加载 `evolve/skills/*/SKILL.md` 的 frontmatter（name / description / triggers），用关键词或 LLM 选 0–1 个 skill 注入（关闭 §10 #2 的最小解）
- **引用日志**：每次实际用到的 memory / skill id 写入 `evolve_log`，否则 §7.2「被引用」无法观测
- **手工 prune 约定**：两周审一次，删 / 归档未引用条目（不必自动化）

### 3. 进化协议是否足够？

**对 MVP 的「防写歪」够用，对「防用歪 / 用乱」不够。**

- **技能失效检测**：需要，但 MVP 用轻量版——连续 N 次路由命中后用户给 👎 / 任务失败则标 `status: suspect`，不自动删。代价低，建议 **MVP 纳入字段，检测逻辑可 M4+**。
- **定期审阅**：需要。建议每两周（与 §7.2 验收对齐）列出「未引用 / 冲突 / suspect」清单。代价：一次 CLI 命令；**应纳入 MVP 习惯，不必做复杂 UI**。

### 4. 技术栈建议：Python CLI 是否最佳起点？

**对作者场景（Windows + Word + 脚本），Python CLI 是合理起点，不是唯一最优。**

- **更轻**：先把 `evolve/` 当 Cursor skills 目录用，验证「沉淀 → 复用」是否发生，再写 `agent-core`（验证进化价值，零内核成本）。
- **更稳**：Python 3.12 + 单一 API + 无 adapter 抽象；Word 先 `python-docx` / 模板复制，COM 后置。
- **不建议 MVP 上 Web / TUI**：§10 #3 里 CLI 足够验证闭环；弃用风险真实，但应靠「两周强制自己用」而非提前做 UI。

### 5. 与现有生态：复用 Cursor skills 还是自建？

**复用 Cursor skills 格式（`SKILL.md` + 目录约定），自建只保留 proposal / evolve_log 协议。**

- §2.2、§8.1 已偏向 SKILL.md——应写死「兼容 Cursor skill 布局」，便于从现有 cheat-* 等导入，也避免双标准。
- 关系定位（§10 #10）：**并存 + 可导入**；my-agent 不是替代 Cursor，是「可便携的个人进化仓 + 可选独立运行时」。

### 6. U 盘方案隐患：是否改为「U 盘只存 evolve，代码在 git」？

**是，应改。** §3.1 #4「整体驻留 U 盘」与 §6.2 可靠性 / 速度张力大。

建议拆分：

| 放哪 | 内容 |
|------|------|
| Git（本机 SSD / 云） | `agent-core/`、docs、依赖锁文件 |
| U 盘（或同步盘） | `evolve/`、`templates/`、`data/`、`workspace/` |
| 本机（非盘） | API key、Python / Node 运行时 |

代价：换机多一步 `git pull` + 装运行时（§6.2 已承认）。收益：代码不因盘损坏 / 慢盘扯进日常开发，进化产物仍便携。§9 R2 的缓解应写成默认架构，而非可选备份。

- [ ] **D2** §6.4：删除或改写「后期可关确认」；破坏性工具确认默认永久开启。

### E. 一条可立即执行（优先）
