# my-agent 项目文档评审

> 评审对象：`docs/PROJECT.md` v0.1.0（2026-07-09）
> 评审依据：`docs/REVIEW-GUIDE.md`
> 评审者：Cursor Agent（LLM 评审）
> 日期：2026-07-09

---

## 总评（1～10 分 + 一句话）

**7 / 10** —— 问题定义和边界划分是同类文档里少见的清醒，但进化协议只设计了「写入」半环，「读取/命中」半环几乎空白，而项目的全部价值恰恰押在后者上。

---

## 优点（4 条）

1. **问题定义准确（§2.1、附录 A）**。承认「通用 Word 无损编辑 5 年内拿不下」并主动放弃，转向「模板 + 定点替换 + 确定性工具（COM/docxtemplater）」，这是业界验证过的正解，不是妥协。附录 A 对 Computer Use 的判断（读不全、点不准、误差累积）也准确。
2. **非目标清单与自动化分层（§3.2、§4.2）划出了清晰边界**。L1～L5 按风险分级、L4/L5 明确不做自动，「进化的是可看见的外挂，不是黑盒自改」这条原则是整个项目可审计性的基石。
3. **Proposal 带 `evidence` 字段（§4.3）**。要求每条进化记录可溯源到具体对话，避免「无源规则」，这是多数同类「自进化 Agent」设计里缺失的一环。
4. **文档有自我怀疑能力**。风险登记（§9）、10 条开放问题（§10）、以及评审指南里的「假优点」挑战表，说明作者没有陷入自我说服，这为多 LLM 评审提供了真实的着力点。

## 问题与风险（按严重程度排序）

### P1（硬伤）：进化闭环缺失「读取侧」设计 —— 见 §4.3 vs §10-Q2

§4.3 的协议详细定义了 提议 → 确认 → 落盘 → 回滚，但这只是「写入」半环。沉淀下来的 memory/skill **下次对话如何被检索、注入上下文、按什么优先级命中**，全文只有一句「新对话自动走路由到该 skill + tool」（§5.2 第 4 步）和 `router.py（待建）`（§8），路由机制本身被推到开放问题 Q2。

这是结构性问题而不是待办事项：**如果命中率低，evolve/ 就是一堆没人读的文件，写入侧做得再精致也没有价值**；如果为了保证命中而把所有 memory/skill 全量注入，又直接触发 R3（context 爆炸）。更矛盾的是，MVP 验收标准（§7.2）已经写了「至少 1 条 skill 被路由命中」——**验收依赖一个尚未设计的机制**。

### P2：MVP 验收指标可被 Goodhart —— 见 §7.2

「`memories/` 条目 ≥ 5 且被实际引用」中，条目数一天就能刷出来，「被实际引用」没有定义（注入过 context 算引用，还是改变了输出才算？）。建议改为结果指标：**至少 1 个真实 Word 任务，走模板链路比手工/通用 Agent 更快且格式零损**。

### P3：确认疲劳会让确认流形同虚设 —— 见 §4.3、§10-Q1

「对话结束或里程碑时」生成 proposal，若每轮都提议，两周内用户大概率进入盲点「接受」模式——此时确认流退化为全自动静默进化（§3.2 明确不做的事），R1（错误规则固化）的核心缓解措施失效。降噪不是可选优化，是确认流成立的前提。

### P4：U 盘作为 primary 存储 + 对话明文落盘 = 丢盘即泄露 —— 见 §6.2、§6.4、§10-Q7

§6.4 只防了 API key，但 `data/conversations/` 全量落盘的对话（含工作文档内容、标书合同细节）就在 U 盘上。U 盘的威胁模型首先是**丢失/被拾取**，其次才是损坏。R2 只登记了「损坏」，漏了「泄露」。

### P5：可插拔 LLM adapter 是 MVP 的隐性负担 —— 见 §6.3

评审指南「假优点」表自己已点破。三家 API 的 tool-call 格式、流式、错误语义各不相同，adapter 层会吃掉 MVP 开发时间且在单用户场景下收益为零。

### P6：L3 工具的「沙箱」只是约定，无技术强制 —— 见 §6.4、附录 B

「默认在 workspace/ 下操作」对一段 Python/PowerShell 脚本没有任何强制力，尤其 Word COM 天然操作 U 盘外的本机资源。个人版可以不做真沙箱，但文档应诚实地把它标为「靠确认流 + 人工审阅兜底」，而非「沙箱」。

### P7：模板策略缺「无模板」退化路径 —— 见 §5.2、§5.3

策略假设用户愿意持续维护 `templates/`。当来了一份没有母版的新文档类型时 agent 做什么（拒绝？半自动帮用户从来件制作母版？），文档没有回答。建议把「从来件文档一键提取为母版」列为 M3 之后的候选 skill。

## 对必答问题的回答

### 1. 最大硬伤是什么？

即上面 P1：**进化协议只有写入半环，检索/路由半环缺失，而验收标准已依赖它**。若只能修一处，就在 §4 增加「4.5 检索与注入」一节，哪怕 MVP 答案简陋到「用户显式点名 skill + 每条 memory 首行一句话摘要全量注入」，也必须是设计过的决定而不是空白。

### 2. MVP 应砍掉什么？

仍偏大。建议砍三项、补一项：

- **砍 LLM adapter（§6.3）**：MVP 绑定一家 API，代码里留一个函数边界即可，不写 adapter 层。
- **砍 SQLite（§6.3、§10-Q6）**：进化元数据几十条量级，JSON + 文件足够，等检索成为瓶颈再迁移。
- **砍自动路由**：MVP 用显式调用（用户说「用 xxx skill」）+ 全量注入 memory 摘要，把自动路由推到 M4 之后。这同时把 P1 从「硬伤」降级为「已知延期项」。
- **补：把 Word 模板工具提前到 M1 之前（调整 §7.3）**。书签替换脚本是纯确定性代码，根本不需要 agent 就能先写出来、先用起来——它是项目唯一真实痛点的直接解，应该第一天就验证价值，而不是排在 M3 等进化协议就绪。顺序建议：M0 文档 → M0.5 独立模板脚本 → M1 CLI → M2 proposal 流 → M3 把脚本收编为 evolved tool。

### 3. 进化协议是否足够？

不够，但缺口大小不同：

- **必须补（MVP 内，代价极低）**：每条 memory/skill 记 `last_used_at` 和命中计数。没有这两个字段，后续任何 prune（R3 的缓解）和失效检测都无从谈起。
- **应补（M4，代价低）**：「命中但没帮上忙」的负反馈通道——用户一句「这条不对」应能定位到具体条目并触发降级/归档。
- **可延后**：定期审阅可以就是「每月翻一遍 evolve_log」的人肉习惯，不必做成机制；`expires_at`/`confidence`（可选深入问题）MVP 不值得做，`confidence` 尤其容易变成没人维护的假精度。

### 4. 技术栈建议：Python CLI 是否最佳起点？

是。Word COM 依赖 pywin32，Python 是唯一顺手的选择；CLI 验证进化闭环也正确。两点修正：

- 如上，砍 adapter 和 SQLite，技术栈表（§6.3）里「可插拔」改为「后期」。
- 「CLI 够快」的假优点挑战成立一半：风险不是慢，是**没有入口就不会想起来用**。建议 MVP 加一个几行代码的启动快捷方式（桌面 .bat / 全局命令），把「插盘 → 开始对话」压到 5 秒内，这比 Web UI 便宜两个数量级且解决同一个弃用风险。

### 5. 与现有生态关系：复用 Cursor skills 格式还是自建？

**复用**。作者已在 Cursor 生态中重度使用 SKILL.md 体系（§2.2 自己承认了灵感来源），自建标准意味着两套格式、无法双向搬运。建议在 §8.1 明确：`evolve/skills/<name>/SKILL.md` 与 Cursor Agent Skills 格式兼容（frontmatter + 触发描述），my-agent 特有的元数据（evidence、命中计数）放在 skill 目录内单独的 `meta.json`，不污染 SKILL.md 本体。代价：格式受制于人；但个人项目跟随一个自己每天在用的格式，弊远小于利。

### 6. U 盘方案隐患：是否改为「U 盘只存 evolve，代码在 git」？

**是，且应更进一步：git 远端是 source of truth，U 盘只是部署介质之一**。§6.2 把 git 定位为「备份」是本末倒置——R2 的正解不是「定期备份 U 盘」，而是 U 盘本身可以随时丢弃重建（clone + 恢复 data）。具体拆分：

| 内容 | 归属 |
|------|------|
| agent-core、evolve/、docs/、templates/ | git（U 盘上是 working copy） |
| data/conversations/ | 默认只存摘要；全文落盘需显式开启且加密（回答 §10-Q7，缓解 P4） |
| API key | 本机（§6.4 已正确） |

## 对其余开放问题的简答（§10）

- **Q1 触发时机**：不要每轮都提议。触发条件收敛为两个——用户显式说「记住这个」，或一次任务成功完成后 agent 检出可复用流程；每次会话 proposal 上限 1～2 条。
- **Q4 本地 embedding**：MVP 不需要。几十个文件量级，文件名 + 首行摘要 + 关键词足够。
- **Q5 Word COM 内置还是 evolved**：**内置**。它是项目的核心价值交付物，不应押在一个尚未验证的进化协议上；进化协议可以用更低风险的东西（比如某个格式偏好 memory）来验证自己。
- **Q9 多 LLM 评审合并**：REVIEW-GUIDE §「提交评审结果的方式」已经给出正确流程（CHANGELOG 记录采纳/拒绝），照做即可，不需要额外机制。

## MVP 范围评价

**略过大，且顺序有误。** 过大在于 adapter、SQLite、自动路由三项各自吞掉开发时间却对两周验收无贡献；顺序错在把项目唯一确定能兑现价值的东西（Word 模板工具）排在 M3，让前两个里程碑都在为一个未验证的「进化」假设打工。反过来排——先用确定性脚本兑现 Word 价值，再让 agent 逐步接管调度——即使进化闭环最终证伪，项目也已经回本。

「两周验收」的时间框架本身是合理的，但按当前指标（条目数）会得到假阳性结论，务必先落实建议 #3。
