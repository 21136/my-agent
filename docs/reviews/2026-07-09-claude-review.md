## 总评（6/10）

**一句话**：问题定义和边界感出色，但「进化」的全部前提——用户愿意且有纪律地持续充当 curator——这个假设从未被检验，而它恰恰是项目成败的支点。

## 优点（与已有评审不重复的部分）

我不重复前两份评审已覆盖的优点（问题定义、非目标清单、进化分层等），它们成立。以下是我认为被低估的亮点：

1. **Proposal 带的 `evidence` 字段（§4.3）是防「无源规则」的真正机制，不是锦上添花。** 多数同类设计要么不记录来源，要么要求每一条都溯源（过于昂贵）。`evidence` 作为必填项+摘要——这个粒度刚好：够轻量以持续记录，够具体以日后审计。这是在「全自动」和「全人工」之间少见的正确切法。

2. **L4/L5 明确「不做自动」（§4.2），且给出了理由而不是空口号。** 内核自改的风险是「难审计」（§3.2），fine-tune 的风险是「成本收益不匹配」——这是工程判断，不是恐惧驱动。开发者能区分「不该做」和「不会做」，文档质量高于典型开源项目。

3. **附录 A 把 Computer Use 定性为「可选工具手段」而非「主路径」（附录 A）**，是对一股潮流的清醒抵制。它没有说 Computer Use 没用——只说不要把排版引擎的责任交给它。这个分寸感在 Agent 设计文档里罕见。

## 最大硬伤（P0）

### 「进化」把用户当成有纪律的 curator，但没有任何机制保证用户会是——而项目的全部差异化价值押在这个假设上。

详细论证：

**首先，看看谁是 curator 以及 curator 要做什么（§4.3、§4.4、§5.2、§9 R3、§10 Q1/Q7/Q8）。**

每一次 proposal 用户要：阅读、理解、决定接受/修改/拒绝、如果是 skill 还要判断「这条会怎么被命中」。冲突时用户还要裁决（§4.4）。膨胀时用户要 prune（§9 R3）。两周后用户要回看 evolve_log 审阅（§7.2 隐含要求）。用户还得维护 templates/ 目录、做 git 备份、管理 U 盘——所有这些是 curator 的职责，不是 agent 的。

**其次，这个角色和「为什么用 Agent」存在根本张力。**

用户用 Agent 是为了**省时间、降认知负荷**。如果每次对话结束 agent 产出 1～3 条 proposal（§10 Q1 尚未收敛），三周后 evolve/proposals/ 堆了 30+ 条，curator 的心理状态不是「太好了我的 agent 在成长」，而是「又一个通知，我先全接受吧」。那一刻确认流退化（前两份评审都提到了确认疲劳），但更深层的问题是：**确认疲劳不是 bug 可以修复——它是 curator 这个角色本身的必然结局，除非 proposal 的命中率 > 90%。**

**第三，看看两周验收标准（§7.2）在 curator 假设下意味着什么。**

「memories/ 条目 ≥ 5 且被实际引用」「至少 1 条 skill 被路由命中」「至少 1 次 Word 模板链路」——这三个指标测的是「系统有没有产出和被使用」，不测「用户有没有因为这个系统变得更轻松」。一个符合全部验收标准的系统，用户可能已经花了更多时间在 review proposal / prune / 调路由上，净收益为负。**验收测了 agent 的成长，没测用户的收益。**

**最后，这个硬伤的根因在文档结构里。**

§4.3 的进化协议画了一个 agent → proposal → 用户的箭头，但画里没有「用户的时间预算」「proposal 的质量门槛」「用户说『今天不看』时系统的行为」。把这几个加上，你会立刻发现：如果用户一周只看一次 proposal，那 §7.2 的「两周验收」就不成立——因为只有 2 次审阅窗口，根本来不及迭代优化路由。

**已有评审都把最大硬伤指向「消费侧空白」。我部分同意——路由没设计确实是执行层硬伤。但路由可以补（下个小节就给方案），curator 假设无法消解——要么接受它并设计降级，要么重新定义「进化」为不需要用户频密审阅的东西。两种选择都会改变 §4.3、§7.1–7.3、§10 Q1/Q8 的答案。** 这比路由空白更底层，因为它决定路由做成什么形态。

## 问题与风险（按严重程度，与前两份尽量不重复）

### P1 — 项目路径假设用户「已有模板」且「模板不过时」，两个假设都脆弱（§5.2–5.3）

§5.2 的进化路径第 2 步是「沉淀 skill——使用 templates/xxx.docx，仅改书签」。这假设用户已经有模板。没有模板时怎么办？文档没写。

但更隐蔽的问题是「模板腐烂」：用户今天做好书签模板，三个月后甲方换了新版式。curator 此时要：发现版式变了 → 重新制作模板 → 替换 skill 引用 → 验证所有旧调用仍兼容。这个维护成本**完全由 curator 承担**，agent 帮不上忙——因为它被设计为「只在壳内替换内容」（§5.3），不检测壳本身是否失效。

建议在 §5 增加「母版生命周期」小节：如何检测书签是否仍存在于当前模板、模板版本号约定、模板过期时 agent 应给出明确警告而非静默写错位置。

### P2 — `evolve/tools/` 的「沙箱」是虚构的安全感（§6.4、附录 B）

「工具脚本默认在 workspace/ 下操作」——这个「默认」对 Python 脚本没有约束力。`os.remove("C:\\Users\\...")` 不会因为脚本放在 `evolve/tools/` 就不执行。Word COM 天然操作 U 盘外的本机资源（打开本地 Word、读写本地文件）。

已有的两份评审都提了「假沙箱」，但我认为需要更具体：**在 §6.4 的「安全边界」小节里加上一句诚实声明**：「当前版本不含技术沙箱；工具脚本的安全性完全依赖：（a）用户人工审阅脚本源码；（b）不关闭确认执行开关。如未来接入社区 skill 或自动化 L3 生成，需在此之前实现进程级沙箱。」这样未来读者不会被「沙箱」措辞误导。

### P3 — 「对话归档全量落盘」的隐私模型缺默认值（§10 Q7）

PROJECT.md 把对话归档设为开放问题（§10 Q7），但在 §8 目录规范里 `data/conversations/` 已经列出来了。读者的自然推断是「会落盘」。U 盘丢失时（§9 R2 只写了损坏，没写丢失），工作文档内容、合同细节、标书信息全部暴露。

建议：默认**不落盘全文**，只存 `conversation_id + timestamp + summary（≤200 字）+ proposal_ids + evolve 触发的条目引用`。全文落盘设为 `--record` flag，且提示「U 盘丢失可导致泄露」。

### P4 — MVP 没有定义「一次对话」的边界（隐含影响 §4.3 触发时机、§7.2 验收）

§4.3 说「对话结束或里程碑时」触发 proposal，但 MVP 是 CLI。CLI 的「对话结束」是用户敲 `exit` / Ctrl+C 还是 session 超时？「里程碑」怎么检测——token 数超阈值、任务标记为 done、还是用户说「好了」？

这个模糊性直接导致 §10 Q1 无法回答：不知道对话边界在哪，就无法设 proposal 频率上限。建议 MVP 定义「对话 = 一次 CLI session，从启动到 exit」；proposal 在用户主动 `exit` 时生成（不是 Ctrl+C），每次 ≤ 2 条。这是最少实现、最可预测的触发模型。

### P5 — 多 LLM 评审合并流程写了但未纳入文档版本号管理（§10 Q9 + 评审指南末尾）

REVIEW-GUIDE 末尾说「更新 PROJECT.md 版本号 + CHANGELOG 记录采纳/拒绝」——但 PROJECT.md 的文档历史（§12）只有一行 0.1.0 初稿。建议在 M0 完成评审后发 0.2.0，把「已关闭的开放问题」「已采纳/拒绝的评审建议摘要」写进 §12。否则几轮评审下来，没人知道文档里哪些是「已决定」、哪些是「仍开放」。已有两份评审加起来 20+ 条具体建议，不版本化管理会很快腐烂。

## 必答问题（6 个）

### 1. 最大硬伤是什么？

见上文 P0：**「用户是 curator」的假设从未被检验，但没有这个角色，整个进化闭环停转。** 路由缺失是执行层硬伤（可修），curator 负担是结构层硬伤（需重新设计假设）。如果只允许指一个，我指 curator 假设。理由：就算路由完美、命中率 100%，如果用户没有精力审 proposal、维护模板、做 prune，evolve/ 要么停止增长（进化死），要么质量下降（进化歪）。

### 2. MVP 应砍掉什么？应增补什么？

**砍：**

| 项 | 出处 | 理由 |
|----|------|------|
| 多 LLM adapter | §6.3 | 单人项目绑一家 API 即可；接口预留一行 |
| SQLite 索引 | §6.3 | 几十条数据量级 JSON + 文件树完全够 |
| 自动 L3 tool 生成 | §4.2 L3 | MVP 仅自动提议 L1 memory + L2 skill |
| 自动路由 | §10 Q2 | MVP 用显式调用（用户说「用 x skill」）+ memory 摘要全量注入 |
| Word COM 作为 M3 硬依赖 | §7.3 M3 | 改为纯 python-docx / 模板复制脚本 |

**增补（小代价高杠杆）：**

| 项 | 理由 |
|----|------|
| conversation 边界定义（§4.3） | 见 P4；不定义就无法设 proposal 频率 |
| `use_count` + `last_used_at` 字段（§4.3） | 前两份评审都提了，这是 prune 和验收的数据基础 |
| 引用日志（`evolve_log` 记每次 memory/skill 实际引用） | 否则 §7.2「被引用」不可观测 |
| 无模板时的降级行为（§5） | 见 P1；最少做到「提示用户提供母版，禁止从零生成复杂 docx」 |
| 母版版本号约定（§5.3） | 见 P1；模板文件名含 version，如 `contract-v2.0.docx` |

### 3. 进化协议是否足够？是否需要「技能失效检测」「定期审阅」机制？

**「写入」半环够用，「读入」半环缺失（已有评审共识）。**

关于失效检测：需要，但不是第一次就要建复杂系统。最小可行版：**每次 skill 被命中后，在任务结束时 agent 问一句「这次用得对吗？」——一句 yes/no + 可选备注。** 连续 3 次 no → 标 `status: suspect`，下次审阅时人工裁决。代价是一个追加的对话轮次（可被用户跳过），MVP 可纳入。

关于定期审阅：需要，且应该比「每月翻一遍」更结构化。建议做一条 CLI 命令 `my-agent review`，输出三张清单：(a) 从未被引用的条目、(b) 冲突对、(c) suspect 条目。用户 5 分钟过一遍。**这比 automate prune 更安全：决定权在人，但发现成本降到最低。**

一个问题前两份评审没提：**proposal 的 `evidence` 字段谁来写？** §4.3 说它是必填项，但 MVP 下只有用户自己或同一个 LLM。如果是同一个 LLM 写 evidence 来论证自己刚生成的 proposal，这就是自我引用循环——证据质量和 proposal 质量绑定。建议 MVP 下 evidence 只需摘录对话原文（不要求分析），把「评估证据力度」留给用户——这降低了 evidence 的虚假权威感。

### 4. 技术栈建议：Python CLI 是否最佳起点？有无更轻/更稳选择？

**Python CLI 是正确起点，理由前两份评审已经展开（COM 友好、脚本生态）。** 我补充一个反直觉的建议：

**M0.5 不要写 agent-core。** 先写一个独立运行的、无 LLM 依赖的 Word 书签替换脚本，放到 `evolve/tools/` 里直接手动调用。这一步的价值：

- 验证「模板 + 定点替换」策略本身是否成立，不依赖任何 agent 假设
- 给 M1 之后的 agent 一个「已被验证有效」的 tool 来调度，而不是让 agent 在未验证的 tool 和未验证的路由之间同时 debug
- 如果这一步就发现「书签替换不够，还需要改样式/段落」，那整个 §5 的策略要提前修正，而不是等到 M3

**即使用户最终只用这个脚本而从未让 agent 调度它，项目也已经回本。** 这是「先让进化层有值得进化的东西」的策略。

### 5. 与现有生态关系：应复用 Cursor skills 格式，还是自建？

**复用，具体方式已有评审给出。** 我补充一个「自建」场景的防御性设计：

即使复用 Cursor `SKILL.md` 格式，仍应给 `evolve/skills/<name>/` 目录留一个 `agent.json`（或 `meta.json`），存放 my-agent 特有的字段：`evidence`、`use_count`、`last_used_at`、`status`、`conflicts_with`。理由是：Cursor 的 SKILL.md 规范未来可能变；my-agent 运行时不应因为上游格式变了就丢失自己的使用数据。**元数据与格式解耦，格式跟随 Cursor，数据自主。**

### 6. U 盘方案隐患：2TB 便携是否应改为「U 盘只存 evolve，代码在 git」？

**是，且还应进一步：git 远端（GitHub/私有 Git）是 source of truth，U 盘是只读部署介质之一。** 前两份评审都给了类似建议，我补充操作层面的具体化：

| 内容 | 归属 | 同步方式 |
|------|------|----------|
| `agent-core/`、`docs/`、依赖锁文件 | Git repo | clone / pull |
| `evolve/`、`templates/` | Git repo（纳入版本控制） | 同上 |
| `data/conversations/` | **不落盘全文**（见 P3）；摘要 + metadata 存 Git | commit |
| `data/state.json` | U 盘本地 + gitignore | 不提交（含本机路径） |
| API key | 本机环境变量 | 手动配置 |
| `workspace/` | U 盘本地 + gitignore | 不提交 |

换机流程：插盘 + `git clone` + 装运行时 + 配 API key。比 §6.1 当前描述的「插盘即用」多一步，但消除了「U 盘坏了全丢」「U 盘丢了全泄露」两个单点。

## MVP 范围评价

### 当前 MVP（§7.1 + §7.3）的判定：**过大，且里程碑排序有问题。**

M1～M4 四个里程碑串行排布，但它们的依赖关系是错的：M3（Word COM 工具）是项目唯一确定能兑现价值的交付，被排在 M1（通用 CLI）+ M2（proposal 流）之后。这意味着前两个里程碑的产出（CLI + proposal）都在为一个尚未验证的核心价值（「模板链路比手工快」）搭脚手架——如果最终验证失败，全部返工。

### 建议的里程碑重排：

| 阶段 | 内容 | 验证什么 |
|------|------|----------|
| M0 | 目录 + 文档 + 本评审修订（发 0.2.0）| 方向对齐 |
| **M0.5 (新增)** | 独立可运行的 Word 书签替换脚本（纯 Python，无 LLM）| **模板策略本身成立** |
| M1 | CLI + 单一 LLM + 3 个基础工具（读文件、列目录、跑 `evolve/tools/` 已有脚本） + 显式 skill 调用 + memory 摘要注入 | agent 调度已验证 tool 的能力 |
| M2 | proposal 生成 + 用户确认流（每会话 ≤ 2 条，仅 exit 时触发） | 进化协议的最小闭环 |
| M3 | 把 M0.5 脚本收编为 evolved tool + 增加第二类文档模板（合同/标书之外的） | 进化协议在真实 tool 上的表现 |
| M4 | git 回滚习惯 + `my-agent review` 命令 + 引用日志审阅 | 治理机制 |

核心变化：**把唯一确定价值的东西从 M3 提到 M0.5——如果它失败了，后面都不用做。**

### 验收标准建议（替代 §7.2 当前指标）：

放弃数量指标（条目 ≥ 5 等），改为：

> **两周后，用户至少完成 1 次「拿一份模板 docx → 替换书签 → 获得格式零损的结果文档」全链路，且用户在 exit 时至少接受了 1 条 proposal（表明愿意 curator）。**

两个条件都测「行为」而非「数量」：模板链路测核心价值，接受 proposal 测 curator 意愿。如果两周后两个条件都满足，项目方向成立；如果只有模板链路成立但 curator 不成立，进化协议需要大改（见 P0）。

## 假优点挑战（对照 REVIEW-GUIDE 表）

| 说法 | 已有评审结论 | 我的补充 |
|------|-------------|----------|
| 「越用越强」 | 无治理时→「越用越乱」 | 真正的问题是**谁来定义「强」**。如果「强」= agent 产出更多 proposal，用户反而更累 |
| 「个人用所以安全」 | tools + 可关确认仍危险 | U 盘丢失的隐私暴露比脚本破坏更可能发生且更难恢复 |
| 「模板解决 Word」 | 对，缺无模板路径 | 缺**模板腐烂**路径——母版过时比没有母版更难发现 |
| 「CLI 够快」 | 验证闭环够用 | 同意；但「快」的前提是 `插盘 → 启动 → 对话` < 5 秒，否则 CLI 再快也用不起来 |
| 「可插拔 LLM」 | MVP 负担 | 不仅是工程负担，还是在伪装灵活性——单人项目换供应商的概率极低 |
