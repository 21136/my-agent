# 项目切换状态隔离

## 问题

切换项目时，侧栏的项目 ID 已经变成新项目，但目标、当前任务、计划建议和会话线仍可能来自旧项目。原因有三类：

1. `project.switch.done` 只更新了 `projectId`，没有清理旧项目的派生状态。
2. 旧的 `context.switch.done` 链路没有通知主项目面板更新项目上下文，导致后续目标项目状态被误判为旧事件。
3. 顶部 `+ 项目` 使用 `command: 项目 新建 <id>`，命令完成后原先没有发标准化的上下文切换完成事件。
4. 切换期间到达的旧项目 `project.state` 或 `project.plan.state` 没有被识别并丢弃，可能在新项目状态之后再次覆盖界面。

## 新建与打开的边界

`+ 项目`对应的是显式的 `项目 新建 <id>`，它只能创建一个尚不存在的项目。若
`workspace/<id>/` 已存在，内核必须返回明确错误，并保持当前会话、当前项目和项目会话映射不变；
不得把“新建”静默降级为“打开”或“续接”。

- 新项目：`项目 新建 <id>`，ID 已存在时失败。
- 已有项目：`项目 打开 <id>` 或 `项目 切换 <id>`，允许续接该项目的专属会话。
- 创建失败：不写入当前会话绑定，不切换侧栏上下文，不生成新的项目会话。

这样可以避免用户通过“项目 +”输入旧项目 ID 后，界面看似切换成功但目标卡、任务和摘要仍属于另一个项目的误判。

## 设计约束

- 项目 ID 是项目状态事件的隔离边界；`project.switch`、`context.switch` 和项目命令三条链路必须共用同一收口。
- 切换开始后，界面显示切换中的空态，不继续展示旧项目的目标、任务和计划提示。
- 切换完成后，只接受目标项目的 `project.state`、`project.plan.state` 和 `project.threads` 事件。
- 迟到的旧项目事件必须无副作用地丢弃。
- 不清理聊天组件的通用消息历史；会话切换仍由 `session.banner` / `session.history` 负责。

## 处理流程

```text
用户选择项目 B
  -> 记录 pendingProjectId=B
  -> 清理项目 A 的派生状态并渲染切换中
  -> 服务端完成切换，发送 project.switch.done(B)
  -> 请求 B 的 project.state / plan.state / threads
  -> 只应用 project_id=B 的事件
  -> 丢弃迟到的 project_id=A 事件
```

## 验收标准

- 从项目 A 切换到项目 B 后，目标摘要、任务阶段、当前任务、建议、文档和会话线不残留 A 的内容。
- 在 B 已成为当前项目后注入 A 的延迟状态事件，B 的界面状态保持不变。
- 新项目的状态事件仍能正常填充目标、任务和计划数据。
- 对已存在 ID 执行“新建”时，当前项目和会话映射保持不变，并展示可执行的打开/切换提示。
